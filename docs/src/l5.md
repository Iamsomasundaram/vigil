# Level 5: Memory

**The question this level answers:** how does the system know what it already did, and what happened next?

Every level so far starts from a blank slate. Ask about the same CVE on day 1 and on day 60 and the model has no idea it ever saw it, whether you patched it, or whether the risk changed. L5 gives the system a memory, and a way to learn from outcomes.

## The idea in plain English

A model does not remember anything between calls (see [How LLMs work](concepts.md)). So "memory" is not something inside the model. It is **your code** saving results to a database, then **pasting the relevant history into the next prompt**. The model reads that history like any other text.

{{flow: Recall ~ read history from the database | Analyse ~ tool loop + that history | Remember ~ save the new result}}

Then, later, a person tells the system what happened (patched, dismissed...). That **feedback** is stored too, so the next run can see it.

## Three kinds of memory

The comment at the top of `levels/l5_memory.py` names three ideas:

| Kind | Plain meaning | Where it lives |
| --- | --- | --- |
| Episodic | "What we did": each past analysis | the `analyses` table |
| Feedback | "What happened": patched, dismissed, in progress... | the `feedback` table |
| Similar incidents | "What looks like this one" | the `analysis_vectors` table |

The third one is covered in its own section below. The "trend awareness" idea in the file's header comment is mostly left to the model: the history it receives includes earlier CVSS and EPSS values, and the prompt tells it to note changes. There is no separate code that computes trends.

## Why a database?

A Python dictionary disappears when the program stops. A database keeps data across restarts and lets you query it. Vigil uses **PostgreSQL**, accessed with `asyncpg` and plain SQL so you can see exactly what runs. The schema is created on first use by `init_db`, which is safe to run repeatedly because every statement says `IF NOT EXISTS`:

{{include levels/l5_memory.py#init_db}}

Two details to notice. The analysis itself is stored in a `JSONB` column, a flexible structured field, so the table does not need a column per result field. And `feedback` points at an analysis through `analysis_id`.

Rows are not a prompt. `build_memory_context` formats them into a readable block, and that block is pasted into the **system prompt** inside `run_memory_aware_loop`:

This technique is called **in-context learning**, the simplest kind of memory: the model is not retrained, it just reads more text. ## Step 3: Remember, and let the database correct the model

After the analysis, `analyse_cve` saves the result. One line deserves attention:

```python
analysis_dict["times_analysed"] = len(history) + 1
```

The model is asked to fill in `times_analysed`, but it can only guess. The database knows the real count, so the code overwrites the model's number before saving. That is a good habit: **let the model write, and let your code own the facts it can compute exactly.**

## Feedback: closing the loop

Memory of what the agent *said* is only half the story. The valuable signal is what *happened*. `record_feedback` stores an outcome against the most recent analysis for that CVE. The status values listed in the code are `patched`, `dismissed`, `in_progress`, `still_vulnerable` and `monitoring`.

Next time the CVE is analysed, `get_history` joins the latest feedback onto each run, and the formatter prints a line such as `Feedback: PATCHED` into the history the model reads.

## Memory can grow: the token budget

History grows without limit, but a model's context window does not. `build_budgeted_memory_context` keeps the injected memory under a token budget, and it explains its priority in its docstring:

1. If everything fits, use it all verbatim.
2. Otherwise keep the most recent few runs verbatim and ask the model to **summarise** the older ones.
3. If that is still too long, drop the summary and then drop the oldest verbatim runs.

It also returns a small report saying how many entries were verbatim, how many were summarised, and whether anything was truncated. Two settings control it, both in `.env.example`:

| Setting | What it does | Default in the code |
| --- | --- | --- |
| `VIGIL_MEMORY_TOKEN_BUDGET` | Maximum tokens of memory injected | 1500 |
| `VIGIL_MEMORY_RECENT_VERBATIM` | How many recent runs are always kept word-for-word | 2 |

Token counts use `tiktoken` when it is installed, and otherwise a rough "about four characters per token" guess, so the project still runs offline. Summarising older entries costs an extra model call, which is one reason the budget exists.

## Similar incidents: semantic recall

`get_history` only finds runs of the **same** CVE. L5 also finds **other** CVEs whose stored summaries look similar, using *embeddings*: lists of numbers that represent text, where similar texts end up close together.

The flow is: after each analysis, a short summary of the result is embedded and saved in `analysis_vectors`. On the next run, `semantic_recall` compares the current CVE's summary with the stored ones using cosine similarity and returns the closest matches above a threshold (0.55 by default, up to 5 results). Those matches are added to the prompt as "relevant prior incidents", with a line telling the model to treat them as data, not instructions.

The embedding method is chosen by `VIGIL_EMBED_MODE`:

| Mode | What it is | Honest limitation |
| --- | --- | --- |
| `local` (the default) | A small deterministic hash-based vector (32 numbers), no network | It only reflects **word overlap**. The code comment says outright that it is not semantic. |
| `openai` | Real embeddings from `text-embedding-3-small` (1536 numbers) | Needs a working API key. On any error the code falls back to the local method instead of crashing. |

So with the default setting, "similar incidents" means "summaries sharing many of the same words". To see genuinely meaning-based matches, switch to `openai` mode. Embeddings and retrieval are explored further in [Retrieval](retrieval.md), and caching ideas in [Semantic caching](semantic-cache.md).

> **Note** Only recent vectors are searched: the query reads the latest 200 stored rows. That is fine for learning, and one of the first things to change at scale.

## Setting up PostgreSQL

L5 and L6 will not run without a database. You have two routes.

**Route A: Docker Compose (simplest).** From the repository root:

```bash
docker compose up --build
```

This starts the API, a PostgreSQL 16 container and Redis, plus the web interface. The Compose file publishes PostgreSQL on port 5432, with the user, password and database all set to `vigil`.

**Route B: your own PostgreSQL.** Create a database and point `DATABASE_URL` at it in `.env`.

About the connection string, which is easy to get wrong:

- The level scripts default to `postgresql://vigil:vigil@localhost:5432/vigil`. That works from your own terminal when the Compose database is running, because the port is published to your machine.
- The API's endpoints default to the same user and password but with host `db`. That name only resolves **inside** the Compose network. If you run the API locally outside Docker, set `DATABASE_URL` yourself.

> **Warning** `vigil:vigil` is a throwaway learning password. Never reuse it anywhere real.

## Run it

With the database up and your API key set:

```bash
python levels/l5_memory.py CVE-2021-44228
python levels/l5_memory.py CVE-2021-44228
python levels/l5_memory.py CVE-2021-44228 --feedback patched --notes "Upgraded the library"
python levels/l5_memory.py CVE-2021-44228
```

What the code is designed to do on each run:

1. **First run:** it reports no prior history, analyses the CVE with live tools, and saves the result.
2. **Second run:** it finds one earlier analysis, shows it in an "Organisation Memory" panel, and passes it to the model.
3. **Feedback run:** it records the outcome and exits without analysing.
4. **Third run:** the history now carries the feedback line, so the model can take it into account.

After each analysis the script prints a context-budget line showing tokens used out of the budget and how many entries were verbatim or summarised. Check that the "Times analysed" figure goes up by one on each analysis run; that number comes from the database count, not from the model.

The same functions are exposed by the API as `POST /l5/analyse`, `POST /l5/feedback`, `GET /l5/history/{cve_id}` and `GET /l5/similar/{cve_id}`, and the web interface has a page for L5.

## Try it

> **Try it** 1) Run the analysis twice, then query the `analyses` table with any PostgreSQL client and look at the JSONB `result` column. 2) Set `VIGIL_MEMORY_TOKEN_BUDGET` very low (for example `200`) and re-run after a few analyses: does the budget line report summarising or truncation? 3) Analyse two different CVEs, then call `GET /l5/similar/{cve_id}` in `local` mode and then `openai` mode, and compare which matches appear. 4) Record `dismissed` feedback with a note and see whether the next analysis mentions it.

## Common mistakes

- **Thinking the model "remembers".** It only sees what you paste into the prompt. If history is not injected, it is not known.
- **Injecting everything.** More history costs more tokens and can drown out the fresh tool data. Budget it.
- **Trusting the model's counts.** Compute facts such as "how many times" in code.
- **Treating local embeddings as semantic.** In the default mode they match shared words, not meaning.
- **Treating stored history as instructions.** Memory is text from the past. The code labels semantic matches as data, and you should keep it that way, because anything stored can influence a later prompt.
- **Forgetting the database is stateful.** Re-running tests or demos against a shared database mixes old and new history. Use a throwaway database for experiments.
- **No privacy plan.** Stored analyses persist indefinitely. See [Privacy](privacy.md) before storing anything sensitive.

## Check yourself

??? Where does the "memory" of an LLM application actually live?
    In your own storage, here PostgreSQL, not in the model. Code reads the history and adds it to the prompt on each call.

??? Why does the code overwrite `times_analysed` after the model answers?
    The model can only guess the count, while the database knows it exactly. Facts your code can compute should not be left to the model.

??? What happens when the memory is too big for its token budget?
    Recent runs are kept verbatim, older ones are summarised, and if that still overflows the summary and then the oldest verbatim runs are dropped. A report records what was done.

??? Why does feedback matter more than the analyses themselves?
    It records what actually happened after the advice, which is the only way the system can tell whether it was followed or useful.

??? In the default embedding mode, why are "similar incidents" not truly similar in meaning?
    The local method hashes words into a small vector, so it reflects word overlap only. Real semantic matching needs the `openai` embedding mode.
