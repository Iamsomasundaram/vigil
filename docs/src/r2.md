# R2: Evaluation

**The question this module answers:** how do I know the agent is any good, and how do I notice when a change makes it worse?

With ordinary code you write a test and it passes or fails. With an agent, "it looked right when I tried it" proves almost nothing: the output varies, and a prompt tweak that fixes one case can quietly break three others. **Evaluation** replaces gut feeling with a repeatable score.

## The idea in plain English

You keep a small exam with known answers (the **golden set**). You run the agent on the exam, grade it several different ways, and save the score. Next time you change a prompt or a model, you run the same exam and compare. If the score drops by more than you allow, the change is rejected. That comparison is a **regression test**.

{{flow: Golden set ~ cases with known answers | Run the agent ~ one output per case | Four metrics ~ each scored 0 to 1 | Overall score ~ the average | Compare to baseline ~ pass or fail}}

## The exam: the golden set

The cases live in `data/eval/golden_set.json`. Each one says what a good answer looks like, not what the exact words must be:

```json
{
  "cve_id": "CVE-2021-44228",
  "expected_severity_band": ["Critical", "High"],
  "expected_kev": true,
  "action_required": true,
  "notes": "Log4Shell should drive urgent remediation."
}
```

The file has three cases: Log4Shell (`CVE-2021-44228`), HTTP/2 Rapid Reset (`CVE-2023-44487`) and Heartbleed (`CVE-2014-0160`). A severity *band* (a list of acceptable values) is used instead of one value because reasonable analysts can disagree between neighbouring levels.

> **Warning** Three cases is a **demonstration**, not a real exam. A real golden set needs dozens to hundreds of varied cases, or a good score tells you very little. The module is built so you can swap in a bigger file with `--dataset`.

## Four ways to grade

`evaluate()` computes four metrics and averages them. Each is a number from 0 to 1 with its own pass mark.

| Metric | What it checks | Passes at |
| --- | --- | --- |
| `deterministic_quality` | Plain code compares the output with the case: is the severity inside the expected band, does the KEV flag match, is action required as expected | 0.8 |
| `llm_judge_quality` | A second model scores the recommendation from 0 to 5 against a written rubric, then the score is divided by 5 | 0.7 |
| `adversarial_injection_resistance` | What fraction of the poisoned fixtures from R1 the scanner flags | 0.9 |
| `faithfulness_grounding` | For L4 only: do the score fields in the answer match what the tools actually returned | 0.8 |

### The judge and its rubric

For qualities that code cannot check, such as "is this recommendation actionable?", a model acts as judge. It is given the rubric in `data/eval/rubric.md`, which defines the scale:

```text
- 0: Unsafe or irrelevant recommendation.
- 1: Mentions the issue but no actionable remediation.
...
- 5: Excellent recommendation: precise, prioritized, and operationally realistic.
```

Written anchors matter. Without them the judge's 3 and your 3 may not mean the same thing. The judge model defaults to the same model as the agent, and `OPENAI_JUDGE_MODEL` lets you pick another.

> **Warning** A judge is a model, so it can be wrong, biased or inconsistent, and a model grading its own family's output tends to be generous. Treat the judge score as a signal to spot-check, not as ground truth. Also note that if the judge call raises an error, the code **silently falls back** to a crude keyword-based heuristic (`_heuristic_judge_score`). The score still appears, so check the logs if a run looks suspiciously smooth.

### What the other two metrics really measure

- **Adversarial** runs R1's scanner over `data/poisoned_cves.json`. It tests the *scanner*, not the agent you are evaluating, so it scores the same for every target.
- **Faithfulness** only applies to `l4`. For every other target it returns 1.0 with the detail "not applicable for non-tool targets".

So for L1 to L3, two of the four metrics give fixed scores. That lifts every overall number and makes real changes look smaller. When you read an overall score, look at the individual metrics too.

After the metrics are averaged, `overall_score` is compared with the saved baseline for that target in `data/eval/baseline.json`:

- `regression_vs_baseline` = overall score minus baseline score.
- `passed_regression` is true when there is no baseline, or when the drop is no larger than `regression_threshold` (default `0.05`).

Pass `--update-baseline` to save the current result as the new baseline. Only do this after a human has agreed the new score is acceptable, or you will bake in a regression.

> **Note** The baseline file in the repository currently holds placeholder entries for `l2` and `l3` (each `overall_score` 0.75, three cases, empty metric lists, cost 0.0). Run `--update-baseline` against your own model before relying on them.

## See it work, offline

You can run the real harness with stand-in functions for the agent and the judge, so nothing calls a model. Here a "good" and a "poor" stub agent are scored against the real golden set (judge scores fixed at 4 and 1):

| Metric | Good stub | Poor stub |
| --- | --- | --- |
| deterministic_quality | 0.889 (8/9 checks) | 0.111 (1/9 checks) |
| llm_judge_quality | 0.8 | 0.2 |
| adversarial_injection_resistance | 1.0 (3/3 flagged) | 1.0 (3/3 flagged) |
| faithfulness_grounding | 1.0 (not applicable) | 1.0 (not applicable) |
| **Overall** | **0.922** | **0.578** |
| Regression vs good baseline | n/a | -0.344, gate FAIL |

The good stub lost one deterministic check because it called `CVE-2023-44487` "Critical", outside the expected `High` or `Medium` band. The numbers come from stub agents written for illustration, not from a real model, so they show how the harness reacts, not how good any model is.

The same idea in code, trimmed from the test suite (`tests/test_evaluation.py`):

```python
scorecard = await r2.evaluate(
    target="l2",
    dataset_path=dataset,
    rubric_path=rubric,
    baseline_path=baseline,

```

Running it against a real level needs an API key:

```bash
python -m reliability.r2_evaluation --target l2
python -m reliability.r2_evaluation --target l2 --update-baseline
```

The targets are `l1`, `l2`, `l3` and `l4`.

## Try it

> **Try it** 1) Copy `data/eval/golden_set.json`, add two cases of your own with a band you believe in, and point `--dataset` at it. 2) In a scratch script, write a `stub_target` that always answers "Low" and confirm the gate fails against a baseline you set. 3) Change a threshold in `_deterministic_score` from `0.8` and see which stub passes.

Run the tests with `python -m pytest tests/test_evaluation.py -q`.

## Common mistakes

- **Too few cases.** A handful of examples cannot represent real traffic.
- **Grading with only one metric.** Each metric has blind spots. The four were chosen to cover each other.
- **Trusting a judge blindly.** Spot-check its scores against your own reading.
- **Updating the baseline to make a failure go away.** That hides the regression instead of fixing it.
- **Testing on the same cases you tuned on.** Once you tune the prompt to a case, it no longer measures anything about new inputs.
- **Evaluating once.** The value is in running it every time something changes.

## Check yourself

??? Why does the golden set use a severity band instead of one expected value?
    Reasonable analysts disagree between neighbouring severities. A band accepts any reasonable answer and still fails clearly wrong ones.

??? Why can an LLM judge not be the only metric?
    It is a model and can be wrong or inconsistent, and the code even falls back to a keyword heuristic if the call fails. Deterministic checks, which plain code can verify, anchor the score.

??? A prompt change drops the overall score from 0.80 to 0.77. Does the gate fail?
    No. The drop is 0.03 and the default allowed drop is 0.05. A drop to 0.74 would fail.
