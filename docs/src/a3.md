# A3: Reflection

**The question this pattern answers:** how do I catch overconfident or incomplete answers *before* the user sees them?

A model's first draft is usually fluent and sure of itself, even when it has gaps. Reflection builds in the habit of every good analyst: write, get reviewed, revise.

## The idea in plain English

Draft a report. Then hand it to a sceptical colleague whose only job is to find problems. Then fix those problems. The "colleague" is the same model, but given an adversarial role.

{{flow: Draft ~ researcher | Critique ~ adversarial reviewer | Revise ~ final report}}

This pattern is about **output quality**. [A1](a1.md) and [A2](a2.md) are about how to *gather* information and *organise actions*. A3 improves what you already produced.

## Why does switching roles help?

The file gives three reasons, and they are good ones:

1. A different role gives a different perspective. The writer who said "patch immediately" may, as reviewer, note that nobody has checked a patch exists.
2. The critic is told to **find problems**, not to evaluate neutrally. That surfaces issues a polite re-read would miss.
3. The reviser sees the draft **and** the critique, so it makes targeted fixes instead of rewriting blindly.

> **Note** These are the pattern's design reasons. Vigil does not measure how much quality improves on real runs, so treat the benefit as a hypothesis you can test yourself (see "Try it").

## Phase 1: research

`research_cve` fetches NVD, EPSS and CISA KEV **in parallel** (they do not depend on each other) using `asyncio.gather`, as in [L2](l2.md). It then makes one model call to write the draft from that raw data. The system prompt says to be factual and to acknowledge uncertainty. The raw data is kept to give to the critic later.

## Phase 2: critique

{{include architectures/a3_reflection.py#critique_draft}}

Two details matter:

- The critic receives the **raw data as well as the draft**, so it can spot claims the data does not support. A critic that only saw the draft could only judge how it reads.
- The prompt is deliberately blunt ("be specific and harsh", "do not be polite") and lists what to check: unsupported claims, missing context, overconfident language, vague recommendations, inconsistent severity and missing caveats.

## The pipeline

{{include architectures/a3_reflection.py#analyse_cve}}

Read the middle carefully. After the critique, the code prints one of two messages depending on `improvement_needed`, but it then calls `revise_draft` **either way**. So the reviser always runs. The test `test_a3_skips_revision_when_critique_says_acceptable` is named as if it skipped revision, but its own docstring explains that revision is intentionally still invoked, and it asserts three model calls.

A run is therefore always **three model calls**, in sequence, plus three data fetches that run together in phase 1.

> **Note** Reflection here is a single pass. The draft is critiqued once and revised once. There is no loop that critiques the revision. Adding "repeat until the critic is satisfied, up to N rounds" is a natural extension, and it would multiply cost.

## Run it

```bash
python architectures/a3_reflection.py CVE-2021-44228
```

You should see the three phases announced in order and the report. The function returns all three stages so a UI can show the draft next to the final version, which is the clearest way to see what reflection did.

## Try it

> **Try it** 1) Print the draft and the final report side by side. Read `changes_from_draft`. Are the changes real improvements or cosmetic rewording? 2) Weaken the critic prompt to "evaluate politely" and compare the critiques. 3) Run a CVE with sparse data (for example a very new one) and see whether the critic flags the gaps and whether the reviser lowers its `confidence`.

## Common mistakes

- **Assuming critique means correctness.** The critic is the same model with the same blind spots. It can miss an error the writer made, or invent a problem that is not there.
- **A neutral critic prompt.** A polite reviewer approves too easily. Ask it to find faults.
- **Critiquing without the source data.** Then it cannot tell grounded claims from invented ones.
- **Paying for polish on easy cases.** Three calls always cost more than one. If the draft is usually fine, consider skipping revision when `improvement_needed` is false.
- **No record of the changes.** Keep `changes_from_draft`, or you cannot audit what the reviser did.

## Check yourself

??? What does the critic see that a plain re-read would not?
    The raw tool data alongside the draft, plus an instruction to hunt for problems. That lets it check each claim against the source.

??? Does the reviser run when the critic says the draft is acceptable?
    Yes. The code logs a different message but still calls `revise_draft`, so a run is always three model calls.

??? How is Reflection different from ReAct?
    ReAct is about gathering information and showing the reasoning behind each tool call. Reflection is about improving the quality of an output after it has been produced.
