# R3: Observability

**The question this module answers:** the agent gave a wrong or slow answer. What exactly happened?

An agent run is a chain of decisions: calls to the model, calls to tools, retries. If all you keep is the final answer, debugging is guesswork. **Observability** means recording enough about each run that you can replay it in your head afterwards.

## The idea in plain English

Each run gets a **trace**: a record of one request from start to finish. A trace is made of **spans**: one per step, such as "call the model" or "fetch NVD data". Spans nest, so you get a tree that shows what called what, how long each took, and how many tokens it used.

{{flow: Trace ~ one run, one id | Span ~ the whole analysis | Span ~ model call, with tokens | Span ~ tool call}}

This is the same model used by industry tracing tools, in a tiny in-process version with no outside service.

## Using it

You open spans with a `with` block. The inner block becomes a child of the outer one automatically:

```python
from reliability import r3_observability as r3

tracer = r3.Tracer()
with tracer.span("analyse", cve_id="CVE-2021-44228"):
    with tracer.span("llm.tool_loop", model="gpt-4o-mini") as s:
        s.add_tokens(950)
    with tracer.span("tool.call", tool="fetch_nvd_data"):
        pass

r3.render_trace_tree(tracer.to_trace())
```

Running exactly that prints a tree like this (the millisecond figures and the trace id will differ on your machine):

```text
analyse [0.1ms] status=ok
├── llm.tool_loop [0.0ms] status=ok tokens=950 model=gpt-4o-mini
└── tool.call [0.0ms] status=ok tool=fetch_nvd_data
trace_id=a91107fb-2a3a-4d4d-bdc1-68d9b9c96856  total=0.1ms  tokens=950  cost=$0.000142
```

Because the code inside the blocks here does nothing, the times are near zero. In a real run each span would show real latency.

## How it works

Spans are managed by a `Tracer`. A small stack tracks which span is currently open, and the span on top of it becomes the parent of the next one. When a block exits, the span is closed, timed and stored. If the block raised an error, the span is marked `error` and the error still propagates, so tracing never swallows an exception.

You can also wrap whole functions, sync or async, with a decorator, so you do not edit every call site:

## What a trace stores

Each span records: a unique id, its parent's id, a name, string attributes, start time, duration in milliseconds, a status of `ok` or `error`, and an optional token count. A finished trace adds the root span id, total duration, total tokens and an estimated cost.

`add_tokens` attributes tokens to the span that is currently open, so you can see *which step* spent them instead of just a grand total.

## Keeping and finding traces

- **In memory:** every finished trace is kept in `TRACE_STORE`, a small store that holds the latest 200 and drops the oldest. Fetch one with `get_trace(trace_id)`. It is lost when the process stops.
- **On disk:** `export_trace_jsonl(trace, path)` appends one trace per line to a file, and `load_trace_jsonl(path, trace_id)` finds one again. JSON Lines is easy to search with ordinary tools.

The API exposes the same idea at `GET /r3/trace/{trace_id}`.

## Limits to know about

> **Warning** 1) **The cost figure is rough.** `to_trace` multiplies the total tokens by a single hard-coded price (0.15 dollars per million, the input price of `gpt-4o-mini`). It does not separate input from output tokens or look up the model, so it usually understates. For real cost attribution use [R5](r5.md). 2) **One stack per tracer.** If several concurrent tasks share a single `Tracer`, their spans can interleave on that stack and get the wrong parent. Give each task its own `Tracer`, or run the steps one after another. 3) **Everything is in-process.** There is no sampling, no shipping to a collector, and no protection for sensitive data. Do not put secrets or personal data in attributes.

> **Warning** A span attribute must not be called `name`. `Tracer.span(self, name, **attributes)` already uses that word for the span's own name, so `tracer.span("tool.call", name="x")` raises `TypeError: got multiple values for argument 'name'`. Use another key, such as `tool`.

## Try it

> **Try it** 1) Run the snippet above, then add a nested span inside `tool.call` and watch the tree deepen. 2) Raise an error inside a span with `raise RuntimeError("boom")` inside a `try` block, and look at its `status`. 3) Export the trace with `r3.export_trace_jsonl(trace, "traces.jsonl")` and open the file in your editor.

The behaviours above are pinned by `tests/test_observability.py`. Run them with `python -m pytest tests/test_observability.py -q`.

## Common mistakes

- **Tracing only the happy path.** Failures are what you most need to see. Errors are recorded automatically, so keep spans around the risky calls.
- **Too much detail in attributes.** Large prompts and responses bloat traces and may hold sensitive text. Record sizes and ids, not full content.
- **Sharing one tracer across concurrent tasks.** See the limits above.
- **Treating the cost number as a bill.** It is an approximation. Use R5 for costs.
- **Never reading the traces.** A trace you do not look at is just disk space. Check them when something is slow or odd.

## Check yourself

??? What is the difference between a trace and a span?
    A trace is the record of one whole run. A span is one timed step inside it, and spans nest to form a tree.

??? Why attribute tokens to a span instead of only keeping a total?
    You can then see which step is expensive, such as the model call or one particular tool, and fix the right thing.

??? Why does the span's error status not hide the exception?
    The span is marked `error` and the exception keeps propagating, so tracing observes failures without changing program behaviour.
