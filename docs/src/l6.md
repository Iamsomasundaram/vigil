# Level 6: Autonomous agent

**The question this level answers:** what changes when the system acts without waiting for you?

In L0 to L5 a person always starts the run: you ask, the system answers. L6 flips that. You add CVEs to a **watchlist** once. After that a background loop checks them on a schedule, notices when something matters, and leaves an alert for you to review.

## Automated versus autonomous

The file's own header draws the line, and it is worth remembering:

| | Who starts the work? | Example |
| --- | --- | --- |
| **Automated** (L1 to L5) | A person or a trigger | You run a level and read the result |
| **Autonomous** (L6) | The system, on its own schedule | The loop scans the watchlist every interval |

The test is simple: does the system **initiate** action, or only **respond** to it?

## The idea in plain English

Imagine a night-shift analyst with a list of CVEs. Every hour they check the latest numbers, compare them with their notes from last time, and write a note only if something meaningfully changed. When you arrive, the notes are waiting.

{{flow: Read watchlist | Fetch live data ~ NVD + EPSS | Compare with last state | Meaningful change? ~ rules in code | Write alert ~ then wait for a human}}

## L6 reuses the earlier levels

L6 is built from pieces you have already met:

| Earlier level | How L6 uses it |
| --- | --- |
| L2, parallel fan-out | `asyncio.gather` fetches NVD and EPSS together, and scans many CVEs at once |
| L4, tools | The same NVD and EPSS data sources, but called as plain functions, not through a model's tool loop |
| L5, memory | A `scan_state` table remembers the last known numbers per CVE, so there is something to compare against |

> **Note** Alert severity is decided by a small lookup table keyed on the change type. It is plain code, not the L3 routing step and not a model call. The file's header comment describes this the same way.

## The most important design choice: rules decide, the model words

Here is the key idea of this level. **Deciding that something changed is done in plain Python, not by the model.** Only the writing of the alert is done by the model.

{{include levels/l6_autonomous.py#detect_changes}}

Read the order of the `if` branches. The first match wins:

1. no earlier state: `new_cve`
2. EPSS crossed 0.50 on this scan: `epss_critical`
3. EPSS rose by at least 0.15: `epss_spike`
4. a patch signal appeared that was not there before: `new_patch`
5. CVSS rose by at least 1.0: `severity_increase`
6. otherwise: `no_change`

The thresholds are two named constants at the top of the file: `EPSS_SPIKE_THRESHOLD = 0.15` and `EPSS_CRITICAL_THRESHOLD = 0.50`.

Why not ask the model "did anything important change?" The docstring explains: a model might treat the same small movement as significant on one run and not on the next. Code gives the same answer every time, can be unit tested, and can be audited. This is a pattern worth copying: **use deterministic code for decisions you must be able to explain, and use the model for language.**

## Turning a change into an alert

Only when the rules find a change does the model get involved:

{{include levels/l6_autonomous.py#generate_alert}}

Look at what the code does **after** the model replies. It builds the final alert from the rule-based signal: the severity, the alert type and the scores all come from code. The model supplies only two pieces of text, the summary and the recommended action. So the model cannot talk its way into a higher or lower severity.

The mapping, from the `severity_map` inside the function, is:

| Change | Alert severity |
| --- | --- |
| `epss_critical` | Critical |
| `epss_spike`, `severity_increase` | Warning |
| `new_patch`, `no_change` | Informational |
| `new_cve` | Warning if the EPSS score is above 0.3, otherwise Informational |

## Scanning one CVE

`scan_one` runs the whole cycle for one CVE: fetch, compare, save the new baseline, and alert if needed.

{{include levels/l6_autonomous.py#scan_one}}

Two details matter.

- **One connection per task.** Many scans run at the same time, and a database connection cannot be shared by overlapping operations. So each `scan_one` opens and closes its own. The comment in the code names the error you would otherwise hit.
- **The baseline is saved whether or not an alert fires.** That way the next scan always compares against the most recent numbers.

## Scanning the whole watchlist

{{include levels/l6_autonomous.py#scan_all_once}}

The scans run in parallel, but a **semaphore** limits it to 5 at a time, because the public NVD API rate-limits callers. `return_exceptions=True` means one failing CVE does not stop the others; the error is printed and the scan continues.

## The loop, and the kill switch

The loop itself is short. It scans, then waits, then repeats until told to stop:

{{include levels/l6_autonomous.py#_monitor_loop}}

The waiting is done with `asyncio.wait_for` on a stop event rather than a plain sleep, so a stop request wakes the loop immediately instead of after the full interval. The interval comes from `VIGIL_SCAN_INTERVAL` in seconds, and the code's default is 3600 (one hour); the comment suggests 60 for demos.

The emergency brake is `stop_monitor`:

{{include levels/l6_autonomous.py#stop_monitor}}

It sets the stop event, cancels the task, waits for it to finish, and reports whether something was actually running. Calling it when nothing is running is harmless. The loop is started by `start_monitor`, which also does nothing if one is already running.

> **Note** The loop is an `asyncio.Task` inside one Python process, which here means inside the API server. If the server restarts, the loop stops and has to be started again. The code comments say a real deployment would use a proper scheduler.

## Human oversight

The code is clear about the limits of its own authority. The agent **detects and alerts; it does not act.** It does not patch systems, open tickets or send email. In the header's words: full autonomy in detection, human authority in response.

Two controls support that:

- **The kill switch**, `POST /l6/monitor/stop`, stops all autonomous activity.
- **Alert acknowledgement**, `POST /l6/alerts/{id}/acknowledge`, records who reviewed an alert and when, using the `acknowledged`, `acknowledged_at` and `acknowledged_by` columns. Unacknowledged alerts stay visible, so there is a trail of what was reviewed.

This is the **human-in-the-loop** idea in its simplest form: the system proposes, a person decides. For the wider treatment of limiting what an agent may do, see [Action governance](r7.md).

## What it stores

`init_db_l6` adds three tables next to L5's:

| Table | Purpose |
| --- | --- |
| `watchlist` | CVEs being monitored, with a soft-delete `active` flag and `last_scanned` |
| `scan_state` | The last known EPSS, CVSS and patch signal per CVE: the baseline for comparison |
| `alerts` | Generated alerts and whether a person has acknowledged them |

## Run it

The command line covers the manual parts:

```bash
python levels/l6_autonomous.py --add CVE-2021-44228
python levels/l6_autonomous.py --add CVE-2023-44487
python levels/l6_autonomous.py --scan
python levels/l6_autonomous.py --status
```

`--scan` performs one pass over the watchlist and prints how many CVEs were scanned and how many alerts were generated. `--status` shows the watchlist and the most recent alerts. There is also `--remove` to take a CVE off the list.

The **continuous loop is not started from the command line.** It runs inside the API server:

```bash
curl -X POST http://localhost:8000/l6/monitor/start
curl http://localhost:8000/l6/monitor/status
curl -X POST http://localhost:8000/l6/monitor/stop
```

Other endpoints cover the watchlist (`/l6/watchlist`), a manual scan (`/l6/scan`) and alerts (`/l6/alerts`). The web interface has an L6 page with the same controls.

What to expect from the code, step by step: the first scan of a CVE has no saved state, so it is classified `new_cve` and an alert is generated for it, even if the risk is low, because the code only skips alerting on `no_change`. From the second scan on, an alert appears only if one of the rules fires. Check the values against NVD and EPSS yourself: the numbers are live and change over time.

## Try it

> **Try it** 1) Add two CVEs and run `--scan` twice in a row. Compare the alerts after the first and the second scan. Which change types appear? 2) Lower `EPSS_SPIKE_THRESHOLD` and `VIGIL_SCAN_INTERVAL`, start the monitor through the API, then watch the console output. 3) Call the kill switch twice and notice that the second call reports nothing was running. 4) Acknowledge an alert through the API and check that `--status` now marks it reviewed. 5) Add a unit test for `detect_changes`: it is a pure function, so you can feed it dictionaries and assert the change type, with no database or model.

## Common mistakes and limits to know about

- **Letting the model decide what is significant.** Keep the decision in code, as this level does.
- **Alert fatigue.** Every non-`no_change` result produces an alert and a model call, including the first sighting of each CVE. Too many alerts teach people to ignore them. Tune the thresholds.
- **Telling "no data" apart from zero.** `fetch_current_epss` returns `None` on any error (network, HTTP status or bad JSON), not `0.0`. `resolve_epss` then falls back to the last known score, so a one-off failure is neither saved as a fake baseline nor turned into a spike on the next scan. `scan_one` prints a short notice when this happens. With no history at all, 0.0 is the only value available, so a failure on a CVE's very first scan still records 0.0.
- **Ideas the code does not implement.** The file's header lists them as future work: a dead band for tiny EPSS movement, and skipping CVEs that already have "patched" feedback. Today, an EPSS rise smaller than 0.15 that does not cross 0.5 simply produces no alert, and every CVE's first scan alerts.
- **No kill switch.** Anything that runs on its own needs a documented way to stop it.
- **Believing it acts.** This agent only informs. Do not give an autonomous loop write access to production systems without the controls in [Action governance](r7.md) and review of its decisions.

## Check yourself

??? What is the difference between automated and autonomous in this project?
    Automated systems run when a person or trigger starts them. An autonomous system starts its own work on a schedule or goal. L6 is autonomous because the loop scans the watchlist without being asked.

??? Why is change detection plain Python instead of a model call?
    It must be consistent, testable and explainable. A model might judge the same small change differently on different runs. The model is used only to write the alert text.

??? Who sets an alert's severity, the code or the model?
    The code. The final alert takes its severity, type and scores from the rule-based signal, and only the summary and recommended action come from the model.

??? Why does each scan open its own database connection?
    Scans run concurrently, and a single connection cannot handle overlapping operations. Each task owns its connection to avoid the "another operation is in progress" error.

??? What does the kill switch do, and is it safe to call twice?
    It sets the stop event and cancels the background task, so the loop ends at once. A second call finds nothing running and simply reports that.

An AI *system* waits for you. An AI *agent* has a goal, uses tools, remembers, and acts without being asked, while a human keeps the brake and the final say. You have now read each of those pieces as running code.

What this project deliberately does not do is make an agent safe to trust. The next sections look at how agents can be structured, and later ones at how to make them reliable and governed.
