# R6: Online evaluation and drift

**The question this module answers:** the system passed its tests last month. How do I know it is still good *today*?

## What goes wrong without it

Offline evaluation, covered in [R2](r2.md), checks the system against a fixed set of examples before release. That is necessary, but it only describes the day you ran it. In production the world moves:

- A provider quietly updates the model behind the name you call.
- Someone edits a prompt, or the data you retrieve changes.
- Real users ask things your test set never covered.
- Responses get slower, or longer and therefore more expensive.

None of these throws an error. The system keeps answering, just a bit worse each week. This is called **drift**, and the only defence is to keep measuring the live system and compare it with what you promised.

## The idea in plain English

Think of a car dashboard. You do not wait for the engine to fail; you watch a few gauges all the time and a warning light tells you when one leaves its safe range.

{{flow: Each real request ~ scored | Rolling window ~ last 200 samples | Compare with the targets ~ SLOs | Recommended action}}

Three terms matter:

- **Online evaluation**: scoring real traffic as it happens, as opposed to a fixed test set.
- **SLO** (service level objective): a target you commit to, such as "average quality at least 0.7".
- **Rolling window**: only the most recent samples count, so old good days cannot hide a bad week.

## Part 1: the targets

The module ships three default SLOs:

Quality is a score from 0 to 1. Latency is in milliseconds. Cost is in US dollars per interaction. These numbers are teaching defaults; a real team would choose its own. You can override any of them when you ask for a report.

## Part 2: recording samples

Each real interaction becomes one sample:

{{include reliability/r6_online_eval_drift.py#record_sample}}

Notice three things:

- **The module does not score quality itself.** You pass `quality` in. In a real system it might come from user ratings, an automated judge, or a rule check. Here it is simply an input, so the module is about *monitoring*, not *judging*.
- **Values are clamped.** Quality is forced into 0 to 1, and latency and cost cannot go below zero.
- **The window is capped at 200.** Older samples fall off the front. The window is a plain Python list in memory, so it is **lost when the process restarts** and is not shared between processes. That is a teaching simplification.

## Part 3: the report

{{include reliability/r6_online_eval_drift.py#drift_report}}

Read it in four steps.

**1. Averages.** It averages quality, latency and cost over the window.

**2. Breaches.** If an average crosses its SLO, it adds a name to `breaches`: `quality_below_slo`, `latency_above_slo` or `cost_above_slo`.

**3. Quality drift.** `quality_drift` is the average quality minus a `baseline_quality` you supply, which defaults to 0.8. A negative number means worse than the baseline.

**4. Sustained drift.** With at least 10 samples, it splits the window in half and compares the first half with the second. If the later half is worse by **0.1 or more**, `sustained_drift` is true. This is how it tells a **bad moment** from a **trend**: one terrible sample barely moves a half-window average, but a lasting decline does.

The last step turns this into a single recommendation:

| Situation | `recommended_action` |
| --- | --- |
| Quality below SLO, or sustained drift | `rollback_or_human_review` |
| Some other SLO breached (latency or cost) | `investigate` |
| Nothing wrong | `healthy` |
| No samples yet | `collect_more_samples` |

Notice that **sustained drift triggers the strongest action even when the average still passes the SLO**. That is the point: the average can look fine while the trend is heading somewhere bad.

## A worked example

This comes from the module's tests. Six samples at quality 0.9, then six at 0.6:

- The average is 0.75, which is above the 0.7 SLO, so there is **no breach**.
- The first half averages 0.9 and the second 0.6, a fall of 0.3, which is over 0.1. So `sustained_drift` is true.
- The result is `rollback_or_human_review`, even though the headline average looked acceptable.

## Run it

```bash
python -m reliability.r6_online_eval_drift
python -m reliability.r6_online_eval_drift --samples 30
```

The demo feeds in made-up samples whose quality falls by 0.02 each time, then prints the report as JSON. No model is called and nothing costs money. With the default 12 samples, the run I checked reported an average quality of 0.74, no breaches, `sustained_drift` true and the action `rollback_or_human_review`. Your numbers should match, because the demo uses fixed inputs.

The same logic is available over HTTP as `POST /reliability/drift/sample` and `POST /reliability/drift/report` when the API is running.

## What is simulated

- The samples in the demo are invented. Nothing here watches real traffic.
- Quality scores are supplied by the caller.
- The window lives in memory only.
- There is no alerting service. The module returns a recommendation; it does not page anyone or roll anything back.

## Try it

> **Try it** 1) Feed in 12 samples all at quality 0.75 and check the action is `healthy`. 2) Add samples with `latency_ms=6000` until `latency_above_slo` appears, and note which action you get. 3) Pass `slo={"min_quality": 0.9}` to `drift_report` and see how the same data now breaches. 4) Record only 9 samples that decline steadily and confirm `sustained_drift` stays false, because the check needs at least 10.

## Common mistakes

- **Watching only the average.** A steady slide can hide under a passing average. Check the trend too.
- **A tiny window.** Too few samples make the numbers jumpy and create false alarms.
- **A huge window.** Too many old samples dilute a real problem so it appears late.
- **No baseline.** Without a reference quality, "drift" has no meaning. Choose and record one.
- **Scoring with a weak signal.** Drift detection is only as good as the quality score you feed it.
- **Acting on one number.** Look at quality, latency and cost together before you roll back.

## Check yourself

??? Why monitor a live system when you already ran an offline evaluation?
    The offline test describes one moment against fixed examples. Models, prompts, data and user behaviour change afterwards, and degradation is usually silent, so you need continuous measurement.

??? How does the module tell a one-off dip from a real trend?
    It compares the average of the earlier half of the window with the later half. A drop of at least 0.1, with at least 10 samples, counts as sustained drift. A single bad sample barely changes a half-window average.

??? Why can the action be `rollback_or_human_review` while no SLO is breached?
    Sustained drift is checked separately from the SLOs. A falling trend can be serious even if the overall average still passes.
