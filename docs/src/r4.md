# R4: Resilience

**The question this module answers:** what does the agent do when a source it depends on is slow, flaky or down?

The agent's tools call outside services: NVD for descriptions, EPSS for exploit likelihood, CISA for the known-exploited list. Services fail. If one failure crashes the whole run, the agent is only as reliable as its flakiest dependency. **Resilience** means failing in a controlled way and still giving the best answer available.

## The idea in plain English

Think of a delivery driver who finds the road closed. A fragile driver gives up. A resilient one tries again once or twice, takes another route if the road stays closed, stops wasting time on that road for a while, and tells you honestly that the parcel is late.

{{flow: Timeout ~ do not wait forever | Retry ~ try again, a little later each time | Circuit breaker ~ stop calling a source that keeps failing | Degrade ~ answer with what you have, and say so}}

## Block 1: timeout and retry

A timeout puts a ceiling on how long one attempt may take. A retry repeats a call that failed for a temporary reason, waiting longer after each failure (**exponential backoff**) plus a little random jitter so many clients do not retry at the same instant.

{{include reliability/r4_resilience.py#with_retry}}

The key detail is `retry_on`. Only errors that are plausibly temporary (`TransientToolError`, `TimeoutError`) are retried. A `NonTransientToolError`, such as a bad request, is raised straight away, because trying the same bad request again cannot help. The tests check this: a non-transient error is called exactly once.

## Block 2: the circuit breaker

If a source keeps failing, retrying it for every request wastes time and can make an outage worse. A **circuit breaker** counts consecutive failures and, past a threshold, *opens*: further calls fail immediately without touching the source.

{{include reliability/r4_resilience.py#CircuitBreaker}}

It has three states:

| State | Meaning |
| --- | --- |
| `closed` | Normal. Calls go through. |
| `open` | Too many failures. Calls are refused instantly with `CircuitOpenError`. |
| `half_open` | After the recovery time has passed, one trial call is allowed. Success closes the circuit; another failure reopens it. |

In this module each source has its own breaker, set to open after **2** consecutive failures and to try again after **2 seconds**. Note that a breaker counts one failure per *whole retried call*, not per attempt, so a source needs two failed calls in a row before its circuit opens.

## Block 3: degrade gracefully

When a source is unavailable the agent does not fail. It builds a verdict from the sources that did respond and says which did not:

{{include reliability/r4_resilience.py#analyse_cve}}

Confidence falls by 0.2 for every degraded source (`1.0 - 0.2 x degraded`, never below 0). Three missing sources gives 0.4. The verdict lists `degraded_sources` and a status for each source, so a reader can see that the answer rests on partial evidence.

## Practice with chaos

Waiting for a real outage is a poor way to test. The module has a built-in **chaos** switch that forces failures on demand:

| Directive | Effect |
| --- | --- |
| `timeout` | The call hangs, then raises a timeout |
| `500` or `transient` | A temporary error, which is retried |
| `400` or `permanent` | A permanent error, which is not retried |
| `flaky` | Fails every other call |

This run forces all three sources to fail. It is safe to run without a key, because the forced failure happens before any network call:

```bash
python -m reliability.r4_resilience --chaos "nvd=500,epss=timeout,kev=400"
```

You should see a table like this:

| Source | Available | Attempts | Circuit |
| --- | --- | --- | --- |
| nvd | no | 3 | closed |
| epss | no | 3 | closed |
| kev | no | 1 | closed |

followed by `Confidence: 0.40` and `Summary: Degraded sources: nvd, epss, kev`.

Read the table as a story. `nvd` and `epss` had temporary-looking failures, so each was tried 3 times (the maximum). `kev` got a permanent error, so it was tried **once**. All circuits are still `closed` because each source has failed only one call so far, and the threshold is two.

Without `--chaos`, the command calls the real services and needs network access.

## Idempotency: safe to retry

Retrying is only safe if repeating a step does no extra harm. If a step writes a record, a retry could write it twice. `idempotent_scan_step(key, action)` remembers the result for a key and returns the stored result instead of running the action again:

{{include reliability/r4_resilience.py#idempotent_scan_step}}

It returns `(ran, result)`: `True` if the action ran this time, `False` if the stored result was reused. The test suite checks that a retried scan does not create duplicate writes. This cache lives in memory, so it protects retries within one process, not across restarts.

## Limits to know about

> **Warning** 1) **The per-attempt timeout is 0.1 seconds.** That suits the offline demo, but it is very tight for real network calls and would likely cause many false timeouts against live services. A real deployment would use a longer value. 2) **State is in memory.** Breaker state and the idempotency cache reset when the process restarts. 3) **Errors are classified by text.** A source error counts as permanent only if its message contains `400`; everything else is treated as temporary. 4) **R4 does not call a model.** It wraps the three data tools, and its own cost estimate is always zero.

## Try it

> **Try it** 1) Run the chaos command with `flaky` for one source and see its attempts. 2) Run `nvd=500` twice inside one Python session using `r4.analyse_cve(...)` and print `r4.get_circuit_states()` to watch a circuit open. 3) Wait longer than the recovery time and call again to see `half_open`.

Run the tests with `python -m pytest tests/test_resilience.py -q`.

## Common mistakes

- **Retrying everything.** Retrying a permanent error wastes time. Classify errors first.
- **Retrying without backoff.** A tight retry loop can hammer a service that is already struggling.
- **No timeout.** One hung call can stall the whole agent.
- **Hiding the degradation.** A confident answer built on missing data is worse than an honest "partial". Always report what was missing.
- **Retrying non-idempotent actions.** Retries need a guard, such as an idempotency key, or you risk double writes.

## Check yourself

??? Why is a permanent error such as a 400 not retried?
    The request itself is wrong, so repeating it will fail the same way. Retries are for failures that might go away on their own.

??? What does an open circuit protect against?
    It stops the agent from wasting time and load on a source that keeps failing, and gives the source room to recover.

??? Why report `degraded_sources` instead of just lowering the answer's quality quietly?
    Readers and downstream code need to know the answer rests on partial evidence so they can discount it or wait.
