# A2: Plan-and-Execute

**The question this pattern answers:** what if I want to see, and approve, what the agent intends to do *before* it does anything?

[A1](a1.md) decides each step after seeing the last result. That is flexible but hard to predict. Plan-and-Execute does the opposite: it separates **thinking** from **doing** completely.

## The idea in plain English

A good project lead writes the plan first, shares it, gets sign-off, and only then starts work.

{{flow: Phase 1: Plan ~ one model call, no tools | Review ~ optional human gate | Phase 2: Execute ~ run each step | Synthesise ~ one model call, final report}}

The agent that plans cannot act. The code that acts does not decide. That separation is the defining feature.

## Why bother?

- **Human oversight.** "The agent plans to isolate this host. Approve?" is better than finding out afterwards.
- **A cheap failure.** If the plan is bad you throw it away having paid for one planning call, not a whole run.
- **An inspectable procedure.** The plan is data you can log, diff and test.

## Phase 2: execute the plan

{{include architectures/a2_plan_execute.py#execute_plan}}

What the executor does, in order:

1. Loops over the steps **one at a time**.
2. For a `tool_call` step it looks the name up in `TOOL_FUNCTIONS` and calls it directly with the CVE ID. **No model call is involved.** An unknown tool name is recorded as an error result and the run continues.
3. It collects every result into `observations` and writes an entry to an `execution_log`.
4. At the `synthesise` step it makes one model call, passing all observations, and returns the structured `PlanExecuteReport`.
5. If the plan never contains a `synthesise` step it raises a `RuntimeError`.

That means a whole run costs **two model calls**: one to plan and one to synthesise. The data fetching in between is ordinary code.

> **Note** The file's introduction mentions re-planning and running independent steps in parallel as benefits of the pattern. The code does neither: the executor says it "does NOT re-plan", and it runs steps sequentially. Treat those as things the pattern *allows*, and a good exercise to add yourself.

## Human-in-the-loop gates

The same file contains a second, gated way to run the pipeline. It adds approval points so a person can stop, edit or reject the plan. The decision data comes from `vigil/models.py`:

| Object | What it holds |
| --- | --- |
| `ApprovalGate` | A pending question: the gate type (`plan`, `action` or `clarification`), a payload to review and a risk level |
| `HumanDecision` | The answer: `approve`, `reject`, `edit` or `request_changes`, with who decided and why |
| `PausedRun` | Where the run is: `pending_plan_approval`, `pending_action_approval`, `executing`, `done` or `aborted` |

The flow, as written in `start_gated_run` and `submit_human_decision`:

1. `start_gated_run` makes the plan and **pauses** at a plan gate. Nothing has executed yet.
2. A person approves, edits the plan, requests changes, or rejects. Rejecting ends the run as `aborted`.
3. If the plan contains a step judged high-risk, a second **action gate** asks for approval of that specific step.
4. Only then does `execute_plan` run, and the run becomes `done`.
5. Every decision is appended to an audit list.

> **Warning** This is a teaching heuristic, not a real risk engine. It looks for words in the step text and tool name. Because the KEV tool is called `check_cisa_kev`, any plan that includes it contains the word "kev" and will trigger the action gate. A production system would classify actions by what they can *change*, not by keywords.

Runs are kept in an in-memory dictionary (`_RUNS`), so they disappear when the process restarts. The design notes are in `specs/E2-human-in-the-loop.md`.

## Try it

> **Try it** 1) Read the plan the model produced. Is every step necessary? Is the order sensible? 2) Change the planner prompt to forbid the KEV tool and see what the report says about exploitation. 3) In a test or a REPL, hand-build an `InvestigationPlan` with an unknown tool name and run `execute_plan` to watch the error path.

## Common mistakes

- **Trusting a plan because it looks tidy.** Review it. A fluent plan can still skip the one step that matters.
- **No path to change course.** A fixed plan cannot react if step 1 reveals something surprising. If you need that, add re-planning or use A1.
- **Letting the planner act.** Keep planning tools-free so the plan really is only a proposal.
- **Treating keyword gates as safety.** See the warning above.
- **Forgetting state is in memory.** A gated run is lost on restart.

## Check yourself

??? Why does the planner call pass no tools?
    So it can only describe steps and never perform them. That is what makes the plan a safe thing to review.

??? How many model calls does a normal A2 run make, and why?
    Two: one to produce the plan and one to synthesise the report. The tool steps in between call your functions directly.

??? What happens when a person rejects a plan at the gate?
    The run's state becomes `aborted`, the gate is cleared, and nothing is executed.
