A3: Reflection

The question this pattern answers: how do I catch overconfident or incomplete answers before the user sees them?

A model's first draft is usually fluent and sure of itself, even when it has gaps. Reflection builds in the habit of every good analyst: write, get reviewed, revise.

The idea in plain English

Draft a report. Then hand it to a sceptical colleague whose only job is to find problems. Then fix those problems. The "colleague" is the same model, but given an adversarial role.

Draftresearcher
→
Critiqueadversarial reviewer
→
Revisefinal report

This pattern is about output quality. A1 and A2 are about how to gather information and organise actions. A3 improves what you already produced.

Why does switching roles help?

The file gives three reasons, and they are good ones:

  1. A different role gives a different perspective. The writer who said "patch immediately" may, as reviewer, note that nobody has checked a patch exists.
  2. The critic is told to find problems, not to evaluate neutrally. That surfaces issues a polite re-read would miss.
  3. The reviser sees the draft and the critique, so it makes targeted fixes instead of rewriting blindly.
Note

These are the pattern's design reasons. Vigil does not measure how much quality improves on real runs, so treat the benefit as a hypothesis you can test yourself (see "Try it").

Three agents, three schemas

The researcher produces a draft:

architectures/a3_reflection.py · DraftAssessment
class DraftAssessment(_Base):
    """
    Initial CVE risk assessment produced by the researcher agent.

    This is the first-pass output — accurate but potentially incomplete.
    The critique will identify what it misses or overstates.
    """
    cve_id:             str
    cvss_score:         float
    cvss_severity:      str
    epss_score:         float     = Field(ge=0.0, le=1.0)
    in_cisa_kev:        bool
    patch_available:    bool
    risk_summary:       str       = Field(description="2–3 sentence risk narrative")
    recommended_action: str
    confidence:         str       = Field(description="high / medium / low — how confident are you in this assessment?")

The critic returns a structured critique, with separate lists for different kinds of problem:

architectures/a3_reflection.py · CritiqueReport
class CritiqueReport(_Base):
    """
    Self-critique produced by the critic agent.

    The critique is the mechanism by which the agent identifies its own
    weaknesses BEFORE the user sees the output.
    """
    overall_quality:    str       = Field(description="good / adequate / poor")
    issues:             list[str] = Field(description="Specific problems found in the draft")
    missing_context:    list[str] = Field(description="Information that should have been included")
    overstatements:     list[str] = Field(description="Claims that go beyond what the data supports")
    improvement_needed: bool      = Field(description="Is revision needed or is the draft acceptable?")
    critique_summary:   str       = Field(description="One-paragraph summary of the critique")

The final report records exactly what changed (changes_from_draft), which makes the improvement visible and checkable.

Phase 1: research

research_cve fetches NVD, EPSS and CISA KEV in parallel (they do not depend on each other) using asyncio.gather, as in L2. It then makes one model call to write the draft from that raw data. The system prompt says to be factual and to acknowledge uncertainty. The raw data is kept to give to the critic later.

Phase 2: critique

architectures/a3_reflection.py · critique_draft
async def critique_draft(draft: DraftAssessment, raw_data: dict) -> CritiqueReport:
    """
    Phase 2: the critic reviews the draft assessment.

    The critic has access to both the draft AND the raw data, so it can
    identify claims in the draft that aren't supported by the data.

    The adversarial framing ("your job is to find problems") is intentional —
    it produces more specific and actionable critiques than neutral evaluation.
    """
    console.print("[dim]  Phase 2: Critic reviewing draft...[/dim]")

    response = await client.chat.completions.create(
        model=MODEL,
        messages=[
            {
                "role": "system",
                "content": (
                    "You are an adversarial security analyst reviewing a CVE assessment written by a colleague. "
                    "Your ONLY job is to find problems with the assessment. Be specific and harsh. "
                    "Check for:\n"
                    "  • Claims not supported by the raw data\n"
                    "  • Missing context that would change the risk picture\n"
                    "  • Overconfident language where uncertainty is warranted\n"
                    "  • Vague recommendations that can't be acted on\n"
                    "  • Severity judgements inconsistent with CVSS + EPSS + KEV combined\n"
                    "  • Missing caveats (auth required? network only? interaction needed?)\n"
                    "Do not be polite. Be specific. A good critique makes the revision better."
                ),
            },
            {
                "role": "user",
                "content": (
                    f"Raw data collected:\n{json.dumps(raw_data, indent=2)}\n\n"
                    f"Draft assessment to critique:\n{json.dumps(draft.model_dump(), indent=2)}"
                ),
            },
        ],
        response_format={
            "type": "json_schema",
            "json_schema": {
                "name":   "CritiqueReport",
                "strict": True,
                "schema": _strict_schema(CritiqueReport),
            },
        },
        temperature=0.3,
        max_tokens=1024,
    )
    _track(response)
    return CritiqueReport.model_validate(json.loads(response.choices[0].message.content))

Two details matter:

  • The critic receives the raw data as well as the draft, so it can spot claims the data does not support. A critic that only saw the draft could only judge how it reads.
  • The prompt is deliberately blunt ("be specific and harsh", "do not be polite") and lists what to check: unsupported claims, missing context, overconfident language, vague recommendations, inconsistent severity and missing caveats.

The pipeline

architectures/a3_reflection.py · analyse_cve
async def analyse_cve(
    cve_id: str,
) -> tuple[DraftAssessment, CritiqueReport, ReflectionReport]:
    """
    Full Reflection pipeline: research → critique → revise.

    Returns all three stages so the UI can show the improvement process,
    not just the final result. Seeing the draft alongside the final report
    makes the quality improvement tangible.
    """
    _reset_usage()
    console.print(f"\n[dim]  Starting Reflection analysis of {cve_id}...[/dim]")
    start = time.perf_counter()

    draft, raw_data = await research_cve(cve_id)
    critique        = await critique_draft(draft, raw_data)

    if critique.improvement_needed:
        console.print(f"[dim]  Critique found {len(critique.issues)} issue(s). Revising...[/dim]")
    else:
        console.print("[dim]  Critique: draft is acceptable. Minor polish only.[/dim]")

    final = await revise_draft(cve_id, draft, critique, raw_data)

    elapsed = time.perf_counter() - start
    console.print(f"[dim]  Completed in {elapsed:.1f}s (3 LLM calls)[/dim]")

    return draft, critique, final

Read the middle carefully. After the critique, the code prints one of two messages depending on improvement_needed, but it then calls revise_draft either way. So the reviser always runs. The test test_a3_skips_revision_when_critique_says_acceptable is named as if it skipped revision, but its own docstring explains that revision is intentionally still invoked, and it asserts three model calls.

A run is therefore always three model calls, in sequence, plus three data fetches that run together in phase 1.

Note

Reflection here is a single pass. The draft is critiqued once and revised once. There is no loop that critiques the revision. Adding "repeat until the critic is satisfied, up to N rounds" is a natural extension, and it would multiply cost.

Run it

python architectures/a3_reflection.py CVE-2021-44228

You should see the three phases announced in order and the report. The function returns all three stages so a UI can show the draft next to the final version, which is the clearest way to see what reflection did.

Try it

Try it

1) Print the draft and the final report side by side. Read changes_from_draft. Are the changes real improvements or cosmetic rewording? 2) Weaken the critic prompt to "evaluate politely" and compare the critiques. 3) Run a CVE with sparse data (for example a very new one) and see whether the critic flags the gaps and whether the reviser lowers its confidence.

Common mistakes

  • Assuming critique means correctness. The critic is the same model with the same blind spots. It can miss an error the writer made, or invent a problem that is not there.
  • A neutral critic prompt. A polite reviewer approves too easily. Ask it to find faults.
  • Critiquing without the source data. Then it cannot tell grounded claims from invented ones.
  • Paying for polish on easy cases. Three calls always cost more than one. If the draft is usually fine, consider skipping revision when improvement_needed is false.
  • No record of the changes. Keep changes_from_draft, or you cannot audit what the reviser did.

Check yourself

What does the critic see that a plain re-read would not?

The raw tool data alongside the draft, plus an instruction to hunt for problems. That lets it check each claim against the source.

Does the reviser run when the critic says the draft is acceptable?

Yes. The code logs a different message but still calls revise_draft, so a run is always three model calls.

How is Reflection different from ReAct?

ReAct is about gathering information and showing the reasoning behind each tool call. Reflection is about improving the quality of an output after it has been produced.
