R5: Cost control

The question this module answers: how do I stop an agent from quietly running up a bill, and know where the money went?

Every model call costs tokens, and agents make many calls. A loop that retries, a prompt that grows each turn, or the same question asked a hundred times can turn a cheap experiment into a surprise invoice. Watching the bill is not enough; you want the system to stop itself.

Note

Every cost figure in this module is an estimate. It uses a small price table of indicative list prices that is copied into the code and is not kept up to date. Provider prices change, so treat the numbers as a rough guide, not a bill. Check your provider's current pricing for real figures.

The idea in plain English

Four habits, each a small piece of code:

Budget guardrefuse a call that would overspend
→
Cachedo not pay twice for the same question
→
Context fittingkeep prompts under a size ceiling
→
Ledgerrecord every call so you can see who spent what

The pipeline for one request

All four live in one function. Read it in order, because the order is the design:

reliability/r5_cost_control.py · execute_with_cost_control
async def execute_with_cost_control(
    *,
    feature: str,
    cve_id: str | None,
    model: str,
    system_prompt: str,
    user_prompt: str,
    tools: list[str] | None,
    call_fn: Callable[[list[dict[str, str]]], Awaitable[dict[str, Any]]],
    context_token_ceiling: int = 4000,
) -> dict[str, Any]:
    messages = [
        {"role": "system", "content": system_prompt},
        {"role": "user", "content": user_prompt},
    ]
    messages = fit_context(messages, token_ceiling=context_token_ceiling)

    key = _CACHE.key_for(model, messages[0]["content"], messages[-1]["content"], tools=tools)
    cached = _CACHE.get(key)
    if cached is not None:
        _LEDGER.record(
            CostEntry(
                feature=feature,
                cve_id=cve_id,
                model=model,
                prompt_tokens=int(cached.get("prompt_tokens", 0)),
                completion_tokens=int(cached.get("completion_tokens", 0)),
                cost_usd=0.0,
                cache_hit=True,
            )
        )
        return {
            "result": cached.get("result"),
            "cache_hit": True,
            "budget_status": _BUDGET.status(),
            "warn": False,
        }

    estimated_prompt_tokens = estimate_tokens_from_messages(messages)
    estimated_completion_tokens = 300
    estimated_cost = estimate_cost_usd(model, estimated_prompt_tokens, estimated_completion_tokens)
    allowed, warn, reason = _BUDGET.check_estimate(estimated_cost)
    if not allowed:
        raise BudgetExceededError(reason or "budget_exceeded")

    payload = await call_fn(messages)
    prompt_tokens = int(payload.get("prompt_tokens", estimated_prompt_tokens))
    completion_tokens = int(payload.get("completion_tokens", 0))
    cost_usd = estimate_cost_usd(model, prompt_tokens, completion_tokens)

    _LEDGER.record(
        CostEntry(
            feature=feature,
            cve_id=cve_id,
            model=model,
            prompt_tokens=prompt_tokens,
            completion_tokens=completion_tokens,
            cost_usd=round(cost_usd, 6),
            cache_hit=False,
        )
    )
    budget_status = _BUDGET.consume(cost_usd)

    _CACHE.put(
        key,
        {
            "result": payload.get("result"),
            "prompt_tokens": prompt_tokens,
            "completion_tokens": completion_tokens,
        },
    )

    return {
        "result": payload.get("result"),
        "cache_hit": False,
        "budget_status": budget_status.model_dump(),
        "warn": warn,
    }

Step by step:

  1. Fit the context. Trim the messages to a token ceiling (default 4000).
  2. Check the cache. Identical request seen before? Return the stored answer, record a zero-cost entry marked as a cache hit, and stop.
  3. Estimate the cost before calling. Prompt tokens are estimated from the text, and the reply is assumed to be 300 tokens.
  4. Ask the budget guard. If the estimate would break a cap, raise BudgetExceededError and the call never happens.
  5. Call the model (through call_fn), then compute the actual cost from the reported token counts.
  6. Record and store. Add a ledger entry, update the budget, and save the result in the cache.

The budget guard

reliability/r5_cost_control.py · BudgetGuard
@dataclass
class BudgetGuard:
    request_cap_usd: float = 0.010
    session_cap_usd: float = 1.000
    warn_ratio: float = 0.80
    session_spent_usd: float = 0.0

    def set_caps(self, request_cap_usd: float, session_cap_usd: float, warn_ratio: float) -> None:
        self.request_cap_usd = max(0.0, request_cap_usd)
        self.session_cap_usd = max(0.0, session_cap_usd)
        self.warn_ratio = min(1.0, max(0.0, warn_ratio))

    def check_estimate(self, estimated_cost_usd: float) -> tuple[bool, bool, str | None]:
        if estimated_cost_usd > self.request_cap_usd:
            return False, False, "request_cap_exceeded"
        if (self.session_spent_usd + estimated_cost_usd) > self.session_cap_usd:
            return False, False, "session_cap_exceeded"

        warn_trigger = self.session_cap_usd * self.warn_ratio
        warn = (self.session_spent_usd + estimated_cost_usd) >= warn_trigger
        return True, warn, None

    def consume(self, cost_usd: float) -> BudgetStatus:
        self.session_spent_usd += max(0.0, cost_usd)
        remaining = max(0.0, self.session_cap_usd - self.session_spent_usd)
        return BudgetStatus(
            limit_usd=self.session_cap_usd,
            spent_usd=round(self.session_spent_usd, 6),
            remaining_usd=round(remaining, 6),
            exceeded=self.session_spent_usd > self.session_cap_usd,
        )

    def status(self) -> BudgetStatus:
        remaining = max(0.0, self.session_cap_usd - self.session_spent_usd)
        return BudgetStatus(
            limit_usd=self.session_cap_usd,
            spent_usd=round(self.session_spent_usd, 6),
            remaining_usd=round(remaining, 6),
            exceeded=self.session_spent_usd > self.session_cap_usd,
        )

There are two caps and a warning level:

  • Request cap (default 0.010 dollars): no single call may be estimated above this.
  • Session cap (default 1.000 dollars): total spend in this process may not exceed this.
  • Warn ratio (default 0.80): once spend reaches 80 percent of the session cap, calls are still allowed but flagged with warn: true.

Refusals carry a reason: request_cap_exceeded or session_cap_exceeded. A refusal is a halt, not a warning, so the agent stops instead of spending anyway.

The cache and the ledger

The cache key is a hash of the model, system prompt, user prompt and tool list, so only a truly identical request hits it. A hit costs nothing and is recorded as such, and the report counts what it would have cost as cache_savings_usd.

The ledger records one entry per call. CostLedger.report() groups spend into totals, by feature, by model, plus the savings from the cache. This is attribution: you see not only that you spent 3 dollars but that most of it came from one feature or one model.

Run the demo

This demo is offline. It uses a fake model function, so nothing is sent anywhere and no key is needed:

python reliability/r5_cost_control.py CVE-2021-44228

It prints a result and the budget status. With the default budget of 0.010 the session cap works out to 0.2, and the output looks like this (the spent figure depends on the prompt text):

{
  "result": { "summary": "Cost-controlled analysis for CVE-2021-44228", "chars_seen": 106 },
  "cache_hit": false,
  "budget_status": {
    "limit_usd": 0.2,
    "spent_usd": 8.8e-05,
    "remaining_usd": 0.199912,
    "exceeded": false

}

Try a tiny budget to see a halt. The command below makes the request cap very small, so the call is refused before it runs:

python reliability/r5_cost_control.py CVE-2021-44228 --budget 0.00001
Note

The cache and ledger live in memory, so they exist only for one process. --report in a fresh process therefore shows an empty report. Inside one Python session, call execute_with_cost_control twice with the same arguments and then get_cost_report() to see a hit and the savings.

Limits to know about

Warning

1) Token counts are guessed before the call. estimate_tokens_from_messages assumes about 4 characters per token. That is a rough rule for English and can be off, especially for code or other languages. 2) fit_context can drop the task. It keeps the first message and removes from the second onwards until the text fits. With a system message and one user message, an over-long request leaves only the system message, so the model never sees the question. A real implementation should summarise or truncate content instead. Check the result when you rely on it. 3) The reply size is assumed. The pre-call estimate uses a fixed 300 completion tokens, so a long answer can cost more than the estimate. 4) State is in memory. Caps, cache and ledger reset when the process restarts, and there is no expiry on cached answers. 5) Two price tables exist. R5 keeps its own PRICING_PER_MILLION and the shared vigil/pricing.py has another. Both are indicative, and they must be kept in step by hand.

Common mistakes

  • Only measuring. A dashboard does not stop a runaway loop. Put a cap in the code path.
  • Caching things that should vary. If the answer depends on live data, a cache can serve stale results. Decide what is safe to cache.
  • No attribution. A single total tells you nothing about what to optimise.
  • Trusting the estimate as the bill. Estimates use a guessed token count and an out-of-date price table.
  • Forgetting per-request and per-session limits are different. One protects against a single huge call, the other against many small ones.

Check yourself

Why check the budget before the call rather than after?

After the call the money is already spent. Checking the estimate first lets the system refuse the call.

What does a cache hit record in the ledger, and why?

A zero-cost entry marked as a hit. The report then shows what it would have cost as savings, so you can see the cache's value.

What goes wrong if the context is trimmed carelessly?

Important content, even the user's question, can be dropped, so the model answers without it. Trimming must preserve what the task needs.
