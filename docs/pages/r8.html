Reliability

R8: AI supply chain

The question this module answers: how do I know the prompt, model policy and tool definitions the agent runs on are the ones we reviewed, and that nobody changed them?

What goes wrong without it

In an AI system, a lot of the "code" is not code. It is text and settings that steer behaviour: system prompts, tool schemas, routing policies. They are easy to edit, rarely reviewed as carefully as source code, and a small change can matter a great deal.

  • An edited system prompt that says "ignore previous safety rules" turns a careful agent into a risky one.
  • A changed model policy can silently route sensitive data to a different, unapproved model.
  • A modified tool schema can make the agent call a tool with different arguments.

This is the AI supply chain: everything your system depends on that you did not write in the main program. Ordinary software has had supply-chain attacks for years; AI adds new, softer targets.

The idea in plain English

Food packaging has a tamper seal. If the seal is broken, you do not eat it, however good it looks. R8 puts a seal on each important artifact: a checksum.

A checksum (here, a SHA-256 hash) is a fixed-length fingerprint computed from content. Change even one character and the fingerprint changes completely. If today's fingerprint does not match the one recorded when the artifact was approved, something changed.

Part 1: the manifest

A manifest is a list of the artifacts you track. Here it is data/manifests/ai_artifacts.json. Each entry records a name, a type, an environment, a provenance, the content itself and the expected checksum. The seeded manifest tracks three artifacts: a prompt, a model policy and a tool schema, all marked as coming from this repository.

Part 2: computing the fingerprint

reliability/r8_supply_chain.py · _checksum
def _checksum(content: str) -> str:
    return hashlib.sha256(content.encode("utf-8")).hexdigest()

The content is turned into JSON with sorted keys before hashing, so the same data always gives the same fingerprint no matter how the keys were ordered.

Part 3: verifying

reliability/r8_supply_chain.py · verify_artifacts
def verify_artifacts(path: str = _DEFAULT_MANIFEST) -> dict[str, Any]:
    """Verify each tracked artifact's checksum against its recorded value."""
    manifest = load_manifest(path)
    results: list[dict[str, Any]] = []
    violations = 0

    for art in manifest.get("artifacts", []):
        name = art.get("name", "unknown")
        recorded = art.get("checksum", "")
        content = json.dumps(art.get("content", ""), sort_keys=True)
        actual = _checksum(content)
        ok = actual == recorded
        if not ok:
            violations += 1
        results.append(
            {
                "name": name,
                "type": art.get("type", "unknown"),
                "env": art.get("env", "unknown"),
                "provenance": art.get("provenance", "unknown"),
                "recorded_checksum": recorded[:16],
                "actual_checksum": actual[:16],
                "verified": ok,
            }
        )

    return {
        "manifest_path": path,
        "n_artifacts": len(results),
        "violations": violations,
        "integrity_ok": violations == 0,
        "artifacts": results,
    }

For every artifact it recomputes the fingerprint and compares it with the recorded one. It reports each result and counts violations. integrity_ok is true only when there are zero. Only the first 16 characters of each checksum are shown in the report, to keep it readable.

Part 4: the promotion gate

Verification alone is not enough, because an untampered artifact can still be a bad one. Promotion needs both:

reliability/r8_supply_chain.py · can_promote
def can_promote(*, path: str = _DEFAULT_MANIFEST, eval_passed: bool) -> dict[str, Any]:
    """Promotion requires both integrity verification and passing evals."""
    integrity = verify_artifacts(path)
    allowed = integrity["integrity_ok"] and bool(eval_passed)
    reasons: list[str] = []
    if not integrity["integrity_ok"]:
        reasons.append("integrity_violation")
    if not eval_passed:
        reasons.append("eval_gate_failed")
    return {
        "allowed": allowed,
        "integrity_ok": integrity["integrity_ok"],
        "eval_passed": bool(eval_passed),
        "reasons": reasons or ["ok"],
    }

→

Evaluation passes
→

If integrity fails the reason is integrity_violation. If the evaluation gate fails the reason is eval_gate_failed. Both can appear together. This links R8 to R2: the eval_passed flag is meant to come from an evaluation run.

Run it

python -m reliability.r8_supply_chain

This prints the verification report for the seeded manifest. On the repository as it stands, I ran it and it listed 3 artifacts with 0 violations and integrity_ok true. Over HTTP the same functions are GET /reliability/supply-chain/verify and POST /reliability/supply-chain/promote.

To see a violation, copy the manifest, change one word in the content of an artifact without updating its checksum, and run python -m reliability.r8_supply_chain --path your-copy.json. The tests do this with a deliberately wrong checksum (deadbeef), and expect one violation.

What is simulated, and an honest limit

  • The checksum is stored next to the content, in the same file. That protects against accidental edits and careless changes, but not against someone who can edit the file: they can change the content and recompute the checksum too. Real supply-chain security needs the trusted fingerprints held somewhere the attacker cannot write, or cryptographic signatures from a key they do not have. The spec for this module explicitly leaves enterprise key infrastructure out of scope.
  • The manifest is a small seeded example, with three artifacts, not a real inventory of everything your system uses.
  • There is no check of third-party packages, model weights or downloaded files. Only the artifacts listed in the manifest are verified.
  • Nothing blocks a release. can_promote returns a decision for a pipeline to enforce.
  • eval_passed is supplied by the caller. This module does not run an evaluation.

Try it

Try it

1) Run the verification, then edit one artifact's content in a copy of the manifest and run it again with --path. Which field of the report shows the problem? 2) Call can_promote(eval_passed=False) on the good manifest and read the reasons. 3) Break the manifest and fail the eval and confirm both reasons appear. 4) Add a fourth artifact to a copy and generate its checksum by hashing the JSON-with-sorted-keys form, as verify_artifacts does.

Common mistakes

  • Tracking only code. Prompts, tool schemas and model policies are part of behaviour; track them too.
  • Believing a stored hash is a signature. A hash in the same place as the data does not stop a determined attacker.
  • Verifying once at build time. Verify at the moment of promotion and again at run time where you can.
  • Treating "untampered" as "good". Integrity says nothing about quality, which is why the gate also needs an evaluation.
  • No provenance. Record where each artifact came from, so a surprise is traceable.

Check yourself

What is a checksum, and what does it tell you?

A fixed-length fingerprint computed from content. If the recomputed value differs from the recorded one, the content changed since it was recorded. It does not say whether the change was good or bad.

Why does can_promote need an evaluation result as well as an integrity check?

An artifact can be unchanged and still poor. Integrity answers "is it the same as approved?", evaluation answers "is it good enough?".

Why does this module not stop a determined attacker who can edit the manifest?

The expected checksum sits in the same file as the content, so they can change both. Real protection needs signatures or fingerprints stored where they cannot write.
