Foundations

Fine-tuning and build-versus-tune decisions

The question this topic answers: my model is not good enough yet. Should I change the prompt, add examples, add retrieval, or train it?

Fine-tuning means continuing a model's training on your own examples. It is powerful and often reached for too early. It costs money and time, it needs good data, and a tuned model is harder to change than a prompt. This topic gives you a decision model and a dataset checker, and it does not train anything.

The idea in plain English

There is a ladder of ways to adapt a model, from cheapest and easiest to change at the bottom to heaviest at the top. Climb only as far as the evidence forces you to.

Prompt onlycheapest
→
Few-shotadd examples
→
RAGadd knowledge
→
LoRA fine-tunesmall adapter
→
Full fine-tuneheaviest

The module lists them in this order, cheapest first:

levels/foundations/finetuning.py · _APPROACHES
_APPROACHES = ["prompt_only", "few_shot", "rag", "fine_tune_lora", "full_fine_tune"]

Three terms help:

  • RAG (retrieval-augmented generation): look up relevant documents at question time and give them to the model. Update the documents, not the model. See retrieval.
  • LoRA: a parameter-efficient way to fine-tune that trains a small add-on (an adapter) instead of the whole model.
  • Full fine-tune: update all the model's weights. The heaviest option.

The advisor

levels/foundations/finetuning.py · recommend_approach
def recommend_approach(
    *,
    task_stability: str = "stable",
    data_volume: int = 0,
    needs_fresh_knowledge: bool = False,
    strict_format: bool = False,
    latency_sensitive: bool = False,
    domain_shift: str = "low",
) -> dict[str, Any]:
    """Recommend an adaptation strategy from task characteristics.

    Heuristic teaching model, not a substitute for empirical evaluation.
    """
    reasons: list[str] = []
    scores: dict[str, float] = {a: 0.0 for a in _APPROACHES}

    # Fresh/changing knowledge favors retrieval over baked-in weights.
    if needs_fresh_knowledge:
        scores["rag"] += 2.0
        reasons.append("fresh knowledge favors RAG over weight updates")
    else:
        scores["fine_tune_lora"] += 0.5

    # Strict output format and stable behavior favor fine-tuning.
    if strict_format and task_stability == "stable":
        scores["fine_tune_lora"] += 1.5
        reasons.append("strict, stable format is a strong fine-tune signal")
    elif strict_format:
        scores["few_shot"] += 1.0
        reasons.append("strict format but unstable task favors few-shot first")

    # Data volume gates fine-tuning viability.
    if data_volume >= 1000:
        scores["fine_tune_lora"] += 1.5
        reasons.append("sufficient labeled data supports LoRA fine-tuning")
    elif data_volume >= 100:
        scores["few_shot"] += 1.0
        reasons.append("small data suits few-shot exemplars")
    else:
        scores["prompt_only"] += 1.0
        reasons.append("little/no data favors prompt engineering first")

    # Latency-sensitive deployments prefer smaller tuned models over long prompts.
    if latency_sensitive:
        scores["fine_tune_lora"] += 0.5
        scores["prompt_only"] += 0.5
        reasons.append("latency pressure favors shorter prompts or tuned models")

    # Large domain shift can justify heavier tuning.
    if domain_shift == "high" and data_volume >= 1000:
        scores["full_fine_tune"] += 1.0
        reasons.append("large domain shift with ample data may justify full fine-tune")

    # Baseline: prompt_only always slightly favored (start simple).
    scores["prompt_only"] += 0.5

    recommended = max(scores, key=lambda k: scores[k])
    ranked = sorted(scores.items(), key=lambda kv: kv[1], reverse=True)

    return {
        "recommended": recommended,
        "ranked": [{"approach": a, "score": round(s, 3)} for a, s in ranked],
        "reasons": reasons,
        "guidance": _guidance_for(recommended),
    }

Read it as a scoring sheet again. The rules, in plain words:

  • Fresh or changing knowledge points to retrieval, because retrieval updates faster than training.
  • A strict output format on a stable task points to LoRA fine-tuning.
  • Data volume is a gate: 1,000 or more examples supports LoRA, 100 or more suits few-shot, and less points to prompt engineering.
  • Latency pressure gives small points to LoRA and prompt-only (shorter prompts or smaller tuned models).
  • High domain shift with 1,000+ examples can justify a full fine-tune.
  • Prompt-only always gets a small baseline bonus: start simple.

The result lists the recommendation, a ranked scoreboard, the reasons, and one sentence of guidance.

Warning

Look at the third row. Even with fresh knowledge needed, LoRA still wins because the data and format points outweigh the retrieval points. A person would probably want retrieval here. This is a limit of the heuristic, not a rule of nature, and it is a good reminder that these scores are a starting point for discussion. The function's own docstring says it is not a substitute for empirical evaluation. The test suite shows RAG winning for fresh knowledge in a smaller-data case; try varying data_volume yourself.

Checking a dataset before you train

If you do decide to tune, bad data wastes the whole run. This function checks a chat-style dataset for common problems:

levels/foundations/finetuning.py · validate_finetune_dataset
def validate_finetune_dataset(records: list[dict[str, Any]]) -> dict[str, Any]:
    """Validate a chat-style fine-tuning dataset for common quality issues."""
    total = len(records)
    valid = 0
    issues: list[str] = []
    seen: set[str] = set()
    duplicates = 0
    empty_completions = 0
    role_errors = 0

    for i, rec in enumerate(records, 1):
        msgs = rec.get("messages") if isinstance(rec, dict) else None
        if not isinstance(msgs, list) or len(msgs) < 2:
            role_errors += 1
            continue

        roles = [m.get("role") for m in msgs if isinstance(m, dict)]
        if "user" not in roles or "assistant" not in roles:
            role_errors += 1
            continue

        assistant_text = " ".join(
            str(m.get("content", "")).strip()
            for m in msgs
            if isinstance(m, dict) and m.get("role") == "assistant"
        ).strip()
        if not assistant_text:
            empty_completions += 1
            continue

        fingerprint = json.dumps(msgs, sort_keys=True)
        if fingerprint in seen:
            duplicates += 1
            continue
        seen.add(fingerprint)
        valid += 1

    if role_errors:
        issues.append(f"{role_errors} record(s) missing valid user/assistant roles")
    if empty_completions:
        issues.append(f"{empty_completions} record(s) with empty assistant content")
    if duplicates:
        issues.append(f"{duplicates} duplicate record(s)")

    quality = round(valid / total, 4) if total else 0.0
    ready = total >= 10 and quality >= 0.9 and duplicates == 0

    return {
        "total": total,
        "valid": valid,
        "duplicates": duplicates,
        "empty_completions": empty_completions,
        "role_errors": role_errors,
        "quality_score": quality,
        "ready_to_train": ready,
        "issues": issues,
    }

Each record should look like {"messages": [...]}, with at least one user and one assistant message. The validator counts records that:

  • lack valid user and assistant roles,
  • have an empty assistant reply, or
  • are exact duplicates of an earlier record.

It then reports quality_score (valid records divided by total) and ready_to_train, which is true only when there are at least 10 records, a quality score of 0.9 or more, and no duplicates. Those thresholds are teaching defaults, written in the code; real projects need far more data and richer checks.

A record with an empty answer, for example, is reported like this:

{"total": 1, "valid": 0, "empty_completions": 1,
 "quality_score": 0.0, "ready_to_train": false,
 "issues": ["1 record(s) with empty assistant content"]}
Note

The validator checks structure only. It cannot tell whether your labels are correct, whether the data is representative, or whether it contains private information. See privacy for the last point.

Run it

python levels/foundations/finetuning.py --data-volume 1500
python levels/foundations/finetuning.py --data-volume 50 --fresh-knowledge

Each prints a JSON recommendation, with no key and no cost. Over the API the advisor is POST /foundations/adaptation/recommend and the dataset check is POST /foundations/finetune/validate.

Note

In the command-line script, --strict-format defaults to on, so it is always on. Call the function directly to test the other case.

Try it

1) Hold everything else fixed and change data_volume through 0, 50, 100, 500, 1000. Where does the recommendation flip? 2) Find inputs that make RAG win. 3) Build a five-record dataset with one duplicate and one empty answer and read the issues. 4) Make a clean ten-record dataset and see ready_to_train become true.

Common mistakes

  • Fine-tuning to add knowledge. Tuning is better at style and format than at facts. Use retrieval for facts.
  • Skipping the cheap rungs. Try a better prompt and a few examples first.
  • Tuning without an evaluation set. You cannot tell if it helped. See R2.
  • Training on unchecked data. Duplicates, empties and private data cost you twice.
  • Treating a heuristic as a verdict.

Check yourself

Why is fine-tuning usually a poor way to give a model fresh facts?

Facts change, and retraining is slow and expensive. Retrieval lets you update the documents instead.

What is LoRA, in one sentence?

A parameter-efficient fine-tuning method that trains a small adapter instead of the whole model.

What would make ready_to_train false even for a clean dataset?

Having fewer than 10 records.
