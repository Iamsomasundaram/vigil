Levels

Level 0: A single call

The question this level answers: how do I get a language model to do one useful thing from code?

Every system in this project, including the autonomous agent at L6, is built on this one move: send messages to a model, read the reply. Understand it well and the rest is composition.

The idea in plain English

You hire a specialist for one job. First you hand over a job description (the system prompt). Then you hand over the task (the user prompt). They write back. That is all L0 does.

Part 1: the job description

The system prompt sets the model's role, tone and limits. Specific beats generic every time.

levels/l0_single_call.py · SYSTEM_PROMPT
SYSTEM_PROMPT = """You are a senior cybersecurity analyst specialising in vulnerability management.
Your job is to explain CVEs clearly and concisely to security teams who need to act fast.

Guidelines:
- Use plain English, not jargon
- Be specific about affected systems and versions
- Explain the real-world risk, not just the CVSS score
- Do not provide exploit code or step-by-step attack instructions
- If you are uncertain about specific details of a CVE, say so explicitly"""

Look at what it does:

  • Defines a role: "senior cybersecurity analyst". This shapes the model's point of view.
  • Sets a style: "plain English, not jargon".
  • Draws a boundary: "do not provide exploit code". Safety rules belong here.
  • Allows honesty: "if you are uncertain... say so". This reduces confident guessing.

Compare with the weak version, "You are a helpful assistant.". The model would still answer, but with no angle, no limits and no guidance.

Part 2: the call

Here is the whole function. Read the comments, which explain each choice.

levels/l0_single_call.py · explain_cve
def explain_cve(cve_id: str) -> str:
    """
    A single LLM call that explains a CVE in plain English.

    This is Level 0 — the atomic unit of all AI systems.
    Input:  a CVE identifier (e.g. CVE-2021-44228)
    Output: a plain-English explanation as a string
    """

    # ─── USER PROMPT ──────────────────────────────────────────────────────────
    # The user prompt is the specific task for this call.
    # It should be:
    #   - Specific (not "tell me about this CVE" but exactly what you need)
    #   - Structured (use sections/bullets to guide the model's response)
    #   - Bounded (tell the model what scope to stay within)

    user_prompt = f"""Explain {cve_id} for a security team that needs to respond quickly.

Cover the following:
1. What is the vulnerability? (one paragraph, plain English)
2. Which systems and versions are affected?
3. How can it be exploited? (describe the attack vector — no exploit code)
4. What is the severity and why?
5. What should defenders do right now?"""

    # ─── THE API CALL ─────────────────────────────────────────────────────────
    # client.chat.completions.create() is the core OpenAI call.
    #
    # The `messages` list is the conversation history:
    #   {"role": "system"}  → the model's instructions/persona
    #   {"role": "user"}    → what the user (or your code) is asking
    #   {"role": "assistant"} → what the model replied (used in multi-turn)
    #
    # temperature controls randomness:
    #   0.0  → always picks the most likely next token  (precise, deterministic)
    #   1.0  → samples more freely                      (creative, varied)
    #   For factual security analysis: 0.2 is a good balance.
    #
    # max_tokens caps the response length.
    #   1 token ≈ 4 characters in English.
    #   600 tokens ≈ ~450 words — enough for a thorough CVE summary.

    _reset_usage()
    response = client.chat.completions.create(
        model=MODEL,
        messages=[
            {"role": "system", "content": SYSTEM_PROMPT},
            {"role": "user",   "content": user_prompt},
        ],
        temperature=0.2,
        max_tokens=600,
    )
    _track(response)

    # ─── EXTRACTING THE RESPONSE ──────────────────────────────────────────────
    # The response is a structured object, not just a string.
    # The actual text lives at: response.choices[0].message.content
    #
    # Why choices[0]?  OpenAI can return multiple completions (n=2, n=3...).
    # We only asked for one (the default), so we always take index 0.

    return response.choices[0].message.content

)
PieceWhat it doesWhy this value
modelWhich model answersRead from OPENAI_MODEL, defaulting to gpt-4o-mini, a cheap, fast model that is good enough here
messagesThe conversation so farSystem prompt first, then the task
temperatureHow adventurous the wording is0.2 keeps factual answers steady
max_tokensA cap on the reply length600 tokens is roughly 450 words, enough for a clear summary and a hard stop on runaway cost

The reply is an object, not a string. The text is at response.choices[0].message.content. The [0] is there because the API can return several alternative answers; you asked for one, so you take the first.

Part 3: the task prompt

The user prompt inside explain_cve is specific, structured and bounded. It asks five numbered questions instead of "tell me about this CVE". Numbered questions produce answers that are easier to read and easier to compare between runs.

Run it

python levels/l0_single_call.py CVE-2021-44228
python levels/l0_single_call.py CVE-2023-44487

You should see a header showing the model and CVE, then a panel with the explanation. Check it against the five questions in the prompt. Does it answer all five?

Warning

Do not trust the details blindly. The model answers from memory, not from a live database. Compare version numbers and severity with the official advisory. Level 4 fixes this by letting the model look things up.

What the code also does

Three small helpers sit above the main function: _reset_usage, _track and get_usage. They add up the tokens used in a run and turn them into an estimated cost. The API and the web interface read these numbers. You can ignore them while learning the core idea.

Which setting gives more varied answers? 2) Replace SYSTEM_PROMPT with "You are a helpful assistant." and compare the quality. 3) Lower max_tokens to 60 and see where the answer is cut off.

Common mistakes

  • A vague system prompt. You get a generic answer. Be specific about role, style and limits.
  • Treating the reply as a fact. It is a draft from a model that can be wrong.
  • No token cap. Long replies cost more and can run on. Always set max_tokens.
  • Expecting identical output each run. Even at low temperature the wording can vary. Design code that tolerates that.
  • Forgetting L0 has no memory. A second call knows nothing about the first.

Check yourself

What are the two messages sent in L0, and what is each for?

A system message that gives the model its role and rules, and a user message that carries the specific task.

Why is temperature 0.2 and not 1.0 here?

A security analysis should be steady and careful. A high value would make answers more varied and more likely to wander.

What is the main weakness of L0 that later levels address?

It is one call from memory: no structure you can program against (L1), no specialists (L2), no live data (L4), no memory (L5).
