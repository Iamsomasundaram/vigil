Level 4: Tool use

The question this level answers: how do I stop the model answering from memory, and make it use real, current data?

This is the biggest conceptual step so far, and the one that turns "a model that talks" into "a model that acts". Take your time with it.

Levels L0 to L3 all ask the model about a CVE from memory. That has real problems:

  • A model has a training cutoff, so new CVEs are unknown to it.
  • CVSS scores get reassessed after publication.
  • EPSS (the probability of exploitation) is updated daily.
  • Patches appear after the model was trained.

So the model may state a score or a patch status that sounds right and is wrong. Level 4 fixes this by letting the model look things up.

The idea in plain English

Imagine an analyst who has read a lot but is offline, versus one who is connected to the internet. L4 connects the analyst.

The model cannot browse by itself and never runs anything itself. Instead it can say, in a structured message, "please call this function with these arguments". Your code runs the function and hands the result back. The model then reads the result and carries on.

Modelasks for a tool
→
Your coderuns it
→
Resultgoes back to the model
→
Modelanswers, or asks again
Note

The key point is who is in control. The model only requests. Your code decides whether and how to run it. That is what keeps tool use safe and auditable.

The two tools

This level gives the model two live data sources. Both are free and need no key.

ToolSourceWhat it returns
fetch_nvd_dataNVD, the US National Vulnerability DatabaseThe official description, CVSS score and severity, publication date and a few references
fetch_epss_scoreEPSS, from FIRST.orgThe probability (0 to 1) that the CVE is exploited in the next 30 days, plus its percentile

EPSS adds context that CVSS lacks. The code's own comment gives the example: a CVSS 9.0 with a tiny EPSS can be less urgent than a CVSS 6.0 with a high one.

Note

This level's code uses only these two tools. The sample asset inventory in data/assets.json is not read here.

Step 1: tell the model what tools exist

A tool is described, not handed over. The description has three parts: a name, a plain-English description the model uses to decide when to call it, and a JSON schema for the arguments.

Read the descriptions closely. They are not documentation for humans; they are instructions to the model. "Use this first" and "Always call this after fetch_nvd_data" steer the order of calls. A vague description means the model guesses wrongly about when to use a tool.

Step 2: write the real functions

These are ordinary async Python functions that call the live APIs. They must return a string, because that is what goes back into the conversation, and they return JSON text so the model can read structure.

levels/l4_tool_use.py · fetch_epss_score
async def fetch_epss_score(cve_id: str) -> str:
    """
    Call the EPSS API and return the exploitation probability score.

    EPSS API docs: https://www.first.org/epss/api
    No authentication required. Updated daily.

    The score is a probability from 0 to 1:
      0.001 = 0.1% chance of exploitation in next 30 days (low)
      0.5   = 50% chance (high)
      0.95  = 95% chance (extremely high)

    The percentile tells you how this CVE compares to all others.
    A score of 0.3 at the 95th percentile means only 5% of CVEs are
    more likely to be exploited — context that CVSS alone doesn't give.
    """
    url = f"https://api.first.org/data/v1/epss?cve={cve_id}"
    try:
        response = await http.get(url)
        response.raise_for_status()
        data = response.json()

        items = data.get("data", [])
        if not items:
            return json.dumps({
                "source": "EPSS",
                "cve_id": cve_id,
                "score":  None,
                "note":   "CVE not found in EPSS database — may be too recent or unscored",
            })

        item = items[0]
        return json.dumps({
            "source":     "EPSS",
            "cve_id":     cve_id,
            "score":      float(item.get("epss",       0)),
            "percentile": float(item.get("percentile", 0)),
            "date":       item.get("date", "unknown"),
            "note": (
                f"There is a {float(item.get('epss', 0)) * 100:.1f}% probability this CVE "
                f"will be exploited in the next 30 days. "
                f"This is higher than {float(item.get('percentile', 0)) * 100:.0f}% of all CVEs."
            ),
        })

    except httpx.HTTPStatusError as e:
        return json.dumps({"error": f"EPSS API returned {e.response.status_code}"})
    except Exception as e:
        return json.dumps({"error": f"EPSS API call failed: {str(e)}"})

Notice how failure is handled. Network errors and bad statuses are caught and returned as {"error": ...} instead of crashing the program. That matters: the error text goes back to the model, which can then say "I could not get the EPSS score" instead of making one up. fetch_nvd_data follows the same pattern, and also prefers CVSS v3.1, then v3.0, then v2.

Step 3: connect names to functions

The model emits a name as text. A dictionary turns that name into a function:

levels/l4_tool_use.py · TOOL_FUNCTIONS
TOOL_FUNCTIONS: dict[str, Any] = {
    "fetch_nvd_data":  fetch_nvd_data,
    "fetch_epss_score": fetch_epss_score,
}

The code that uses it is the boundary between the model's world and the real world:

levels/l4_tool_use.py · _execute_tool
async def _execute_tool(tool_call, source: str = "inline") -> str:
    """
    Execute a single tool call and return its result as a string.

    This is the boundary between the LLM world and the real world:
    the model asks → we execute → we return the result.
    """
    fn_name   = tool_call.function.name
    arguments = json.loads(tool_call.function.arguments)

    if (source or "inline").lower() == "mcp":
        try:
            from vigil_mcp.vigil_server import call_tool as mcp_call_tool

            return await mcp_call_tool(fn_name, arguments)
        except Exception:
            # Graceful fallback to inline path if MCP is unavailable.
            pass

    fn = TOOL_FUNCTIONS.get(fn_name)
    if fn is None:
        return json.dumps({"error": f"Unknown tool: {fn_name}"})
    return await fn(**arguments)

If the model asks for a tool that is not in the dictionary, it gets back an error string instead of an exception. This is the same safe-dispatch behaviour you practise in the l4_tool_dispatch exercise below.

Step 4: the loop

This is the heart of the level. The code's docstring describes it as the core primitive:

messages = [system, user]
while True:
    response = llm(messages, tools=TOOLS)
    if response has tool_calls:
        run each tool, append the request and the result, loop again
    else:
        break   # final answer
levels/l4_tool_use.py · run_tool_loop
async def run_tool_loop(cve_id: str, tool_source: str = "inline") -> tuple[GroundedAnalysis, list[dict]]:
    """
    The core of L4: run the LLM in a loop until it stops calling tools.

    The conversation starts with a system prompt and user request.
    On each iteration:
      1. Call the LLM (with the current conversation + available tools)
      2. If the model emits tool_calls → execute each tool, append results, loop
      3. If the model produces a final text response → parse and return

    Returns: (GroundedAnalysis, tool_call_log)
      - GroundedAnalysis: the final structured report
      - tool_call_log: record of every tool call made (for transparency / display)

    The tool_call_log is important for auditability: users can see exactly
    which APIs were called and what they returned, not just the final summary.
    """
    # ── Initial conversation ───────────────────────────────────────────────────
    # The system prompt explains the agent's job and the tools available.
    # It also sets an expectation: use the tools, don't rely on memory.
    messages: list[dict] = [
        {
            "role": "system",
            "content": (
                "You are a vulnerability intelligence analyst. "
                "You have access to two live data sources: NVD (official CVE database) "
                "and EPSS (exploitation probability scoring). "
                "ALWAYS call both tools before providing analysis — never rely on training data alone. "
                "Your final analysis must be grounded in the data you retrieve."
            ),
        },
        {
            "role": "user",
            "content": (
                f"Analyse {cve_id}. "
                "Fetch the NVD data and EPSS score, then provide a grounded risk assessment."
            ),
        },
    ]

    tool_call_log: list[dict] = []  # Records every tool call for display
    openai_tools = tools_for_openai(tool_source)
    iterations   = 0
    max_iterations = 10  # Safety limit — prevents runaway loops

    # ── The loop ──────────────────────────────────────────────────────────────
    while iterations < max_iterations:
        iterations += 1
        console.print(f"[dim]  Iteration {iterations}: calling LLM...[/dim]")

        response = await client.chat.completions.create(
            model=MODEL,
            messages=messages,
            tools=openai_tools,                   # tool menu can come from inline or MCP discovery
            tool_choice="auto",                   # model decides whether to call tools
            # Note: no response_format here — we'll get either tool_calls OR text,
            # not a JSON schema response. We add the schema on the FINAL call.
            temperature=0.1,
            max_tokens=4096,
        )

        _track(response)
        message = response.choices[0].message

        # ── Check: did the model call any tools? ──────────────────────────────
        if message.tool_calls:
            # The model wants to call one or more tools.
            # Append its message first (OpenAI requires this ordering).
            messages.append(message.model_dump(exclude_unset=True))

            # Execute each tool call in parallel — if the model asks for both
            # NVD and EPSS simultaneously, we fetch both at once.
            tool_results = await asyncio.gather(*[
                _execute_tool(tc, source=tool_source) for tc in message.tool_calls
            ])

            for tool_call, result_str in zip(message.tool_calls, tool_results):
                fn_name = tool_call.function.name
                args    = json.loads(tool_call.function.arguments)

                console.print(f"[dim]    → tool: {fn_name}({', '.join(f'{k}={v}' for k, v in args.items())})[/dim]")

                # Log it for the display layer
                tool_call_log.append({
                    "tool":      fn_name,
                    "arguments": args,
                    "result":    json.loads(result_str) if result_str.startswith("{") else result_str,
                })

                # Inject the result back into the conversation.
                # The model will read this on the next iteration.
                messages.append({
                    "role":         "tool",
                    "tool_call_id": tool_call.id,
                    "content":      result_str,
                })

            # Loop back — model now has tool results and will decide what to do next
            continue

        # ── No more tool calls: model produced a final response ───────────────
        # At this point the model has all the data it needs.
        # We make one more structured call to get the final GroundedAnalysis.
        console.print("[dim]  Tools complete. Requesting structured final report...[/dim]")

        final_response = await client.chat.completions.create(
            model=MODEL,
            messages=messages + [
                {
                    "role": "user",
                    "content": (
                        "Based on the live data you just retrieved, produce the final structured analysis. "
                        "Use only facts from the tool results — do not add information from training memory."
                    ),
                }
            ],
            response_format={
                "type": "json_schema",
                "json_schema": {
                    "name":   "GroundedAnalysis",
                    "strict": True,
                    "schema": _strict_schema(GroundedAnalysis),
                },
            },
            temperature=0.1,
            max_tokens=2048,
        )

        _track(final_response)
        analysis = GroundedAnalysis.model_validate(
            json.loads(final_response.choices[0].message.content)
        )
        return analysis, tool_call_log

    # If we hit max_iterations without a final response, something went wrong
    raise RuntimeError(f"Tool loop exceeded {max_iterations} iterations — agent may be stuck")

Walk through one imagined pass, following the code (the exact calls depend on the model):

  1. The conversation starts with a system prompt that says: use both tools, never rely on training data alone. The user message asks for a grounded risk assessment.
  2. The model is called with the tool menu and tool_choice="auto", which lets the model decide whether to call a tool.
  3. If the reply contains tool_calls, the loop first appends the model's own message (the API requires that ordering). Then it runs every requested tool at the same time with asyncio.gather, the parallel trick from L2.
  4. Each result goes back as a message with role: "tool" and the matching tool_call_id, so the model knows which request each answer belongs to. Every call is also written to tool_call_log.
  5. The loop goes round again. Now the model has real data in its context.
  6. When a reply has no tool calls, the model is done gathering. The code makes one more call, this time with a JSON schema, to get a typed GroundedAnalysis.

The loop has a safety cap: max_iterations = 10. If the model is still calling tools after ten rounds, the function raises an error instead of running forever or spending money without limit.

Warning

Any loop where a model controls what runs needs a hard cap like this. Without it, one confused response could loop indefinitely and bill you for every round.

Step 5: the grounded result

levels/l4_tool_use.py · GroundedAnalysis
class GroundedAnalysis(_Base):
    """
    Final analysis produced after the agent has fetched live data.

    Every numeric field here comes from a real API call — the model cannot
    invent these values because they were injected into its context as tool
    results. This is the grounding guarantee.
    """
    cve_id:             str
    cvss_score:         float  = Field(description="From NVD API — real current score")
    cvss_severity:      str    = Field(description="Critical / High / Medium / Low")
    epss_score:         float  = Field(ge=0.0, le=1.0, description="Exploitation probability (0–1) from EPSS API")
    epss_percentile:    float  = Field(ge=0.0, le=1.0, description="How this CVE ranks among all CVEs by exploitation likelihood")
    description:        str    = Field(description="Official NVD description")
    patch_available:    bool
    recommended_action: str    = Field(description="What to do, grounded in the live data")
    data_sources:       list[str] = Field(description="Which APIs were actually called")

The final instruction to the model says to use only facts from the tool results. The field descriptions say where each number comes from ("From NVD API", "from EPSS API"), and data_sources records which APIs were actually called. The schema constrains the shape. The grounding comes from what was put into the conversation. If a tool failed, the model has no real value to report, which is why watching the tool log matters.

Two ways to supply the tools: inline and MCP

So far the tools were defined inside the file. That is the inline source and the default. Level 4 can also discover tools from an MCP server.

MCP, the Model Context Protocol, is a standard way for a program to publish tools that any compatible agent can discover and call, instead of each agent hard-coding its own. In Vigil, vigil_mcp/vigil_server.py publishes the same two tools.

The switch is a setting:

VIGIL_TOOL_SOURCE=inline    # the default
VIGIL_TOOL_SOURCE=mcp
levels/l4_tool_use.py · discover_tools
def discover_tools(source: str = "inline") -> list[dict]:
    """Return tool metadata in DiscoveredTool-like shape."""
    source = (source or "inline").lower()
    if source != "mcp":
        out: list[dict] = []
        for row in INLINE_TOOLS:
            fn = row["function"]
            out.append(
                {
                    "name": fn["name"],
                    "description": fn["description"],
                    "input_schema": fn["parameters"],
                    "source": "inline",
                }
            )
        return out

    try:
        from vigil_mcp.vigil_server import list_tools as mcp_list_tools

        return mcp_list_tools()
    except Exception:
        # Graceful fallback when MCP deps/server path are unavailable.
        return discover_tools("inline")

Two things to notice. Whatever the source, tools are described in one common shape (name, description, input_schema, source), and tools_for_openai converts that into the format the model API expects. And there is a graceful fallback: if the MCP path fails for any reason, the code quietly uses the inline tools, so the level still runs. Because of that fallback, a successful run does not prove MCP was actually used; check the source field if you need to know.

Run it

python levels/l4_tool_use.py CVE-2021-44228

This one needs a network connection as well as your API key, because the tools call NVD and EPSS live. It prints a line for each loop iteration and each tool call, then a Tool Calls section with one panel per call and a preview of what came back, then a Grounded Analysis panel with CVSS, EPSS, patch status, data sources and a recommended action. I have not captured sample output here; the numbers come from live services and change over time.

Compare it with your L0 answer for the same CVE. Where the two differ, the tool-based one can be traced to an API response, which is the whole point.

Note

NVD limits unauthenticated use to about 5 requests per 30 seconds (this is stated in the code's comments). If you run the level repeatedly you may see an error returned from the tool. That is the safe error path at work, not a crash.

Common mistakes

  • Vague tool descriptions. The model picks tools using them. Write them like instructions.
  • Letting tool errors crash the program. Return the error as data so the model can react to it.
  • No iteration cap. An uncapped loop can run, and bill, without end.
  • Running whatever the model asks. Always look the name up in an allow-list dictionary. Never eval model output.
  • Assuming grounded means correct. The data is only as good as the source and the call. A failed lookup gives the model nothing to ground on.
  • Hiding the tool log. It is your audit trail. Keep it.

Check yourself

Who actually runs a tool, the model or your code?

Your code. The model only emits a request with a name and arguments. Your dispatcher runs the matching function and returns the result.

Why does the loop append the tool result as a role: "tool" message with a tool_call_id?

So the model can match each result to the request that produced it, and read it on the next iteration.

What stops the loop running forever?

max_iterations, set to 10. If it is reached, the code raises an error.

What does it mean for the analysis to be "grounded"?

Its facts come from data retrieved in this run (NVD and EPSS responses placed in the conversation), not from the model's training memory.

What happens if you set the tool source to MCP and the server is unavailable?

The code falls back to the inline tools, so the level still runs.
