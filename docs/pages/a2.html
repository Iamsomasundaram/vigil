Architectures

A2: Plan-and-Execute

The question this pattern answers: what if I want to see, and approve, what the agent intends to do before it does anything?

A1 decides each step after seeing the last result. That is flexible but hard to predict. Plan-and-Execute does the opposite: it separates thinking from doing completely.

The idea in plain English

A good project lead writes the plan first, shares it, gets sign-off, and only then starts work.

Phase 1: Planone model call, no tools
→
Reviewoptional human gate
→
Phase 2: Executerun each step
→
Synthesiseone model call, final report

The agent that plans cannot act. The code that acts does not decide. That separation is the defining feature.

Why bother?

  • Human oversight. "The agent plans to isolate this host. Approve?" is better than finding out afterwards.
  • A cheap failure. If the plan is bad you throw it away having paid for one planning call, not a whole run.
  • An inspectable procedure. The plan is data you can log, diff and test.

The plan is a typed object

architectures/a2_plan_execute.py · PlanStep
class PlanStep(_Base):
    """
    A single step in the investigation plan.

    step_type distinguishes between steps that call tools and the final
    synthesis step that uses accumulated results to write the report.
    """
    step:        int
    description: str  = Field(description="What this step does and why it is needed")
    step_type:   Literal["tool_call", "synthesise"]
    tool_name:   str  = Field(description="Tool to call (empty string if step_type is synthesise)")
architectures/a2_plan_execute.py · InvestigationPlan
class InvestigationPlan(_Base):
    """
    The complete plan produced by the planner LLM call.

    The plan is produced BEFORE any execution. Each step is a discrete unit
    that the executor will carry out in order.
    """
    goal:        str            = Field(description="Restatement of the investigation goal")
    steps:       list[PlanStep] = Field(description="Ordered steps to achieve the goal")
    reasoning:   str            = Field(description="Why these steps, in this order?")

Each step is either a tool_call (name a tool) or the final synthesise. Because the plan has a schema (the same idea as L1), code can read it, validate it and even let a person edit it.

Phase 1: make the plan

architectures/a2_plan_execute.py · create_plan
async def create_plan(cve_id: str) -> InvestigationPlan:
    """
    Phase 1: ask the LLM to produce a complete investigation plan.

    The planner has no tools — it cannot DO anything here.
    It only produces a structured list of steps to execute later.

    This separation is the defining feature of Plan-and-Execute:
    the agent that plans is different from the agent that acts.
    """
    response = await client.chat.completions.create(
        model=MODEL,
        messages=[
            {
                "role": "system",
                "content": (
                    "You are an investigation planner for a CVE intelligence system. "
                    "Your ONLY job is to produce a step-by-step plan for investigating a CVE. "
                    "Do NOT execute any steps yourself — just plan. "
                    "\n\n"
                    "Available tools for the executor to use:\n"
                    "  fetch_nvd_data   — get CVSS score, severity, description from NVD\n"
                    "  fetch_epss_score — get exploitation probability (0–1) from EPSS\n"
                    "  check_cisa_kev   — check if CVE is in CISA's active exploit catalog\n"
                    "\n"
                    "Each step must be one of: tool_call (call a tool) or synthesise (final report). "
                    "The last step must always be synthesise. "
                    "Think about what information is needed and in what order."
                ),
            },
            {
                "role": "user",
                "content": f"Create an investigation plan for {cve_id}.",
            },
        ],
        response_format={
            "type": "json_schema",
            "json_schema": {
                "name":   "InvestigationPlan",
                "strict": True,
                "schema": _strict_schema(InvestigationPlan),
            },
        },
        temperature=0.1,
        max_tokens=1024,
    )
    _track(response)
    return InvestigationPlan.model_validate(json.loads(response.choices[0].message.content))

Note what is missing: the call passes no tools. The planner can only describe steps, never run them. The prompt names the three tools, says the last step must be synthesise, and says "do NOT execute any steps yourself".

Phase 2: execute the plan

architectures/a2_plan_execute.py · execute_plan
async def execute_plan(
    cve_id: str,
    plan: InvestigationPlan,
) -> tuple[PlanExecuteReport, list[dict]]:
    """
    Phase 2: execute each step in the plan.

    The executor is responsible for:
    - Calling the right tool for each tool_call step
    - Passing all accumulated observations to the synthesis step
    - Producing the structured final report

    The executor does NOT re-plan — it executes what the planner decided.
    If a tool fails, the result includes the error and execution continues.
    """
    observations: list[dict] = []  # Accumulates results from every step
    execution_log: list[dict] = []

    for step in plan.steps:
        console.print(
            f"[dim]  Step {step.step}: {step.step_type}"
            + (f" → {step.tool_name}" if step.tool_name else "")
            + f" | {step.description[:60]}[/dim]"
        )

        if step.step_type == "tool_call":
            # Validate the tool exists before calling it
            if step.tool_name not in TOOL_FUNCTIONS:
                result = {"error": f"Unknown tool: {step.tool_name}"}
            else:
                fn     = TOOL_FUNCTIONS[step.tool_name]
                result = await fn(cve_id)

            observations.append({
                "step":      step.step,
                "tool":      step.tool_name,
                "result":    result,
            })
            execution_log.append({
                "step":        step.step,
                "description": step.description,
                "tool":        step.tool_name,
                "result":      result,
                "status":      "error" if "error" in result else "ok",
            })

        elif step.step_type == "synthesise":
            # The synthesis step uses all collected observations to produce
            # the final report. No tool is called here — the LLM synthesises.
            obs_json = json.dumps(observations, indent=2)

            final_response = await client.chat.completions.create(
                model=MODEL,
                messages=[
                    {
                        "role": "system",
                        "content": (
                            "You are a CVE analyst. Produce a final structured risk report "
                            "based only on the data provided. Do not invent any values."
                        ),
                    },
                    {
                        "role": "user",
                        "content": (
                            f"CVE under investigation: {cve_id}\n\n"
                            f"Data collected from {len(observations)} steps:\n{obs_json}\n\n"
                            "Produce the final risk report."
                        ),
                    },
                ],
                response_format={
                    "type": "json_schema",
                    "json_schema": {
                        "name":   "PlanExecuteReport",
                        "strict": True,
                        "schema": _strict_schema(PlanExecuteReport),
                    },
                },
                temperature=0.1,
                max_tokens=2048,
            )
            _track(final_response)
            report = PlanExecuteReport.model_validate(
                json.loads(final_response.choices[0].message.content)
            )
            execution_log.append({
                "step":        step.step,
                "description": step.description,
                "tool":        "synthesise",
                "status":      "ok",
            })
            return report, execution_log

    raise RuntimeError("Plan had no synthesise step — cannot produce final report")

What the executor does, in order:

  1. Loops over the steps one at a time.
  2. For a tool_call step it looks the name up in TOOL_FUNCTIONS and calls it directly with the CVE ID. No model call is involved. An unknown tool name is recorded as an error result and the run continues.
  3. It collects every result into observations and writes an entry to an execution_log.
  4. At the synthesise step it makes one model call, passing all observations, and returns the structured PlanExecuteReport.
  5. If the plan never contains a synthesise step it raises a RuntimeError.

That means a whole run costs two model calls: one to plan and one to synthesise. The data fetching in between is ordinary code.

Note

The file's introduction mentions re-planning and running independent steps in parallel as benefits of the pattern. The code does neither: the executor says it "does NOT re-plan", and it runs steps sequentially. Treat those as things the pattern allows, and a good exercise to add yourself.

Human-in-the-loop gates

The same file contains a second, gated way to run the pipeline. It adds approval points so a person can stop, edit or reject the plan. The decision data comes from vigil/models.py:

ObjectWhat it holds
ApprovalGateA pending question: the gate type (plan, action or clarification), a payload to review and a risk level
HumanDecisionThe answer: approve, reject, edit or request_changes, with who decided and why
PausedRunWhere the run is: pending_plan_approval, pending_action_approval, executing, done or aborted

The flow, as written in start_gated_run and submit_human_decision:

  1. start_gated_run makes the plan and pauses at a plan gate. Nothing has executed yet.
  2. A person approves, edits the plan, requests changes, or rejects. Rejecting ends the run as aborted.
  3. If the plan contains a step judged high-risk, a second action gate asks for approval of that specific step.
  4. Only then does execute_plan run, and the run becomes done.
  5. Every decision is appended to an audit list.

What counts as "high-risk" is a simple keyword check:

architectures/a2_plan_execute.py · _is_high_risk_step
def _is_high_risk_step(step: PlanStep) -> bool:
    text = (step.description + " " + step.tool_name).lower()
    return any(k in text for k in ("critical", "offline", "shutdown", "immediate"))
Warning

This is a teaching heuristic, not a real risk engine. It looks for words in the step text and tool name. Because the KEV tool is called check_cisa_kev, any plan that includes it contains the word "kev" and will trigger the action gate. A production system would classify actions by what they can change, not by keywords.

Runs are kept in an in-memory dictionary (_RUNS), so they disappear when the process restarts. The design notes are in specs/E2-human-in-the-loop.md.

Try it

Try it

1) Read the plan the model produced. Is every step necessary? Is the order sensible? 2) Change the planner prompt to forbid the KEV tool and see what the report says about exploitation. 3) In a test or a REPL, hand-build an InvestigationPlan with an unknown tool name and run execute_plan to watch the error path.

Common mistakes

  • Trusting a plan because it looks tidy. Review it. A fluent plan can still skip the one step that matters.
  • No path to change course. A fixed plan cannot react if step 1 reveals something surprising. If you need that, add re-planning or use A1.
  • Letting the planner act. Keep planning tools-free so the plan really is only a proposal.
  • Treating keyword gates as safety. See the warning above.
  • Forgetting state is in memory. A gated run is lost on restart.

Check yourself

Why does the planner call pass no tools?

So it can only describe steps and never perform them. That is what makes the plan a safe thing to review.

How many model calls does a normal A2 run make, and why?

Two: one to produce the plan and one to synthesise the report. The tool steps in between call your functions directly.

What happens when a person rejects a plan at the gate?

The run's state becomes aborted, the gate is cleared, and nothing is executed.
