Reliability

R7: Action governance

The question this module answers: now that the agent can do things, what is it allowed to do, and who decides?

What goes wrong without it

Until L4, the model only produced text. Once it can call tools such as "open a ticket" or "apply a patch", a mistake stops being a wrong sentence and becomes a wrong action. Real ways this goes wrong:

  • A confused or manipulated model calls a destructive tool it should never have had.
  • An agent built for read-only analysis is reused somewhere with write access, and nobody notices.
  • A prompt-injection in a document, like the planted entries in data/poisoned_cves.json, talks the agent into acting.

You cannot make the model perfectly obedient. So you move the safety out of the prompt and into code that the model cannot argue with.

The idea in plain English

A building does not rely on visitors being polite. It uses badges: your badge opens some doors, not others, and the server room also needs a second person to sign off.

Three principles are at work:

  • Least privilege: each role gets only the tools it needs.
  • Sandbox levels: the same tool can be used safely, simulated, or for real.
  • Human approval: dangerous real actions need a person to say yes.

Part 1: the policy table

All the rules live in one small data structure.

reliability/r7_action_governance.py · _ROLE_POLICIES
_ROLE_POLICIES: dict[str, dict[str, Any]] = {
    "viewer": {
        "allowed_tools": ["fetch_nvd_data", "fetch_epss_score"],
        "max_sandbox": "read_only",
        "sensitive_tools": [],
    },
    "analyst": {
        "allowed_tools": ["fetch_nvd_data", "fetch_epss_score", "open_ticket"],
        "max_sandbox": "simulate",
        "sensitive_tools": ["open_ticket"],
    },
    "responder": {
        "allowed_tools": ["fetch_nvd_data", "fetch_epss_score", "open_ticket", "apply_patch"],
        "max_sandbox": "execute",
        "sensitive_tools": ["open_ticket", "apply_patch"],
    },
}

Read it as a matrix:

RoleTools allowedHighest sandboxNeeds approval for
viewerthe two lookup toolsread_onlynothing
analystlookups and open_ticketsimulateopen_ticket
responderlookups, open_ticket, apply_patchexecuteopen_ticket, apply_patch

The three sandbox levels escalate in a fixed order: read_only is the lowest, then simulate, then execute. read_only means look but do not change anything. simulate means show what would happen. execute means really do it.

An unknown role gets nothing: get_role_policy falls back to no tools and read_only. That is deny by default, which is the safe direction for a failure.

Part 2: the check

reliability/r7_action_governance.py · check_action
def check_action(
    *,
    role: str,
    tool: str,
    requested_sandbox: str = "read_only",
    approved: bool = False,
) -> dict[str, Any]:
    """Evaluate whether an action is permitted under least-privilege policy."""
    policy = get_role_policy(role)
    reasons: list[str] = []

    if requested_sandbox not in _SANDBOX_ORDER:
        return {
            "role": role,
            "tool": tool,
            "requested_sandbox": requested_sandbox,
            "allowed": False,
            "effective_sandbox": "read_only",
            "requires_approval": False,
            "reasons": ["invalid_sandbox_mode"],
        }

    tool_allowed = tool in policy["allowed_tools"]
    if not tool_allowed:
        reasons.append("tool_not_in_role_scope")

    within_sandbox = _SANDBOX_ORDER[requested_sandbox] <= _SANDBOX_ORDER[policy["max_sandbox"]]
    if not within_sandbox:
        reasons.append("sandbox_exceeds_role_limit")

    is_sensitive = tool in policy["sensitive_tools"]
    requires_approval = is_sensitive and requested_sandbox == "execute"
    approval_ok = (not requires_approval) or approved
    if requires_approval and not approved:
        reasons.append("requires_human_approval")

    allowed = tool_allowed and within_sandbox and approval_ok
    effective = requested_sandbox if allowed else "read_only"

    return {
        "role": role,
        "tool": tool,
        "requested_sandbox": requested_sandbox,
        "allowed": allowed,
        "effective_sandbox": effective,
        "requires_approval": requires_approval,
        "reasons": reasons or ["ok"],
    }

The function asks three questions and collects a reason for each failure:

  1. Is the tool in this role's list? If not: tool_not_in_role_scope.
  2. Is the requested sandbox within the role's limit? If not: sandbox_exceeds_role_limit.
  3. Is human approval needed and missing? Approval is required only when the tool is sensitive for that role and the request is for execute. Missing approval adds requires_human_approval.

The action is allowed only if all three pass. When it is denied, effective_sandbox falls back to read_only, so a caller that ignores the denial still cannot do more than look. An invalid sandbox name is rejected outright with invalid_sandbox_mode.

Returning the reasons matters. A bare "denied" teaches nobody anything; a list of reasons tells the developer, and an auditor later, exactly which rule fired.

Worked examples

These come from the module's tests and from running the demo.

  • A viewer asks to run apply_patch for real. Denied: the tool is not in the viewer's scope.
  • A responder asks to run apply_patch for real, with no approval. Denied with requires_human_approval, and requires_approval is true.
  • The same request with approved=True. Allowed, with effective_sandbox of execute.
  • An analyst asks to run open_ticket for real, even with approval. Denied: an analyst's ceiling is simulate, so approval cannot lift it past the role limit.

That last case is the important design point: approval does not override role limits. It only unlocks actions the role could legitimately do.

Run it

python -m reliability.r7_action_governance
python -m reliability.r7_action_governance --role responder --tool apply_patch --sandbox execute
python -m reliability.r7_action_governance --role responder --tool apply_patch --sandbox execute --approved

The default arguments ask an analyst to execute apply_patch. I ran that and it was denied with both tool_not_in_role_scope and sandbox_exceeds_role_limit, with effective_sandbox set to read_only. Adding --approved did not change that result, which shows approval cannot rescue a request the role was never allowed to make. Over HTTP the same check is POST /reliability/action/check.

What is simulated

  • Nothing here actually blocks a tool call. check_action returns a decision. It is up to the calling code to obey it. In this repo it is a teaching module and a separate API endpoint, not a gate wired around every tool.
  • The approved flag is a plain argument. There is no real approval workflow, identity check or audit log, so anyone calling the function can pass approved=True.
  • The roles are hard-coded in the file, not loaded from a policy system.
  • Sandboxes are labels. There is no real isolation such as a container or restricted account behind read_only or simulate.
Warning

Do not read this as a finished security control. It shows the shape of a good policy check. In production the decision must be enforced where the tool runs, the approval must come from an authenticated person, and every decision must be logged.

1) Call check_action for each role against each tool and sandbox, and fill in your own table. Does it match the matrix above? 2) Pass an unknown role such as "intern" and read the result. 3) Pass requested_sandbox="launch" and note the reason. 4) Add a new role to _ROLE_POLICIES for an auditor who may only read, and write a test for it.

Common mistakes

  • Putting the rule in the prompt. "Never apply patches" can be argued away. A code check cannot.
  • Giving every role every tool for convenience. Start narrow and widen only when needed.
  • Letting approval override limits. Approval should unlock allowed actions, not extend power.
  • Denying without a reason. You will not be able to debug or audit it.
  • Checking only at the start. Check every action, because an agent's plan can change mid-run.
  • Forgetting the default. Unknown role, tool or mode should mean "no".

Check yourself

Why is a policy check in code safer than an instruction in the prompt?

A model can be persuaded, confused or injected into ignoring an instruction. Code runs the same way regardless of what the model says.

An analyst asks to execute open_ticket and a human approves. Why is it still denied?

The analyst role's highest sandbox is simulate, and execute is above it. Approval only matters when the request is otherwise within the role's limits.

What does effective_sandbox protect against?

If a request is denied it falls back to read_only, so a caller that mishandles the denial still cannot change anything.
