Reliability

R9: Release safety

The question this module answers: I improved a prompt, a model choice or a retrieval setting. How do I ship it without risking every user at once?

What goes wrong without it

The obvious way to release a change is to switch everyone over. With AI systems that is especially risky, because:

  • A change that looks better on your ten test examples can be worse on real traffic.
  • Output is not exactly repeatable, so one good demo proves little.
  • By the time complaints arrive, every user has already been affected.

Careful teams release in stages and keep an exit open at each one.

The idea in plain English

Think of testing a new recipe in a restaurant. First the chef cooks it in the back and tastes it against the usual dish, with no customer served. Then a few tables get it. Only if those tables are happy does it go on the menu. If they are not, the old dish comes straight back.

Shadowrun quietly, no users affected
→
Canarya small share of users
→
Full releaseeveryone
  • Shadow: the new version runs on the same inputs as the live one, but its answers are never shown to users. You only compare quality.
  • Canary: the new version serves a small percentage of real traffic. (The name comes from the canary taken into mines to warn of danger early.)
  • Rollback: switching back to the previous version when the canary does worse.

Part 1: shadow comparison

reliability/r9_release_safety.py · shadow_compare
def shadow_compare(*, live_scores: list[float], shadow_scores: list[float]) -> dict[str, Any]:
    """Shadow mode: run new variant with zero user impact and compare quality."""
    live_avg = _mean(live_scores)
    shadow_avg = _mean(shadow_scores)
    return {
        "live_avg": live_avg,
        "shadow_avg": shadow_avg,
        "delta": round(shadow_avg - live_avg, 4),
        "shadow_safe_to_canary": shadow_avg >= live_avg - 0.02,
    }

You give it quality scores for the live version and for the shadow version on comparable work. It reports both averages, the difference, and shadow_safe_to_canary. That flag is true when the shadow average is no more than 0.02 below the live average. So shadow mode is a cheap, risk-free first filter: a version that already looks worse never reaches a real user.

Part 2: the canary decision

reliability/r9_release_safety.py · evaluate_release
def evaluate_release(
    *,
    control_scores: list[float],
    treatment_scores: list[float],
    canary_percent: int = 10,
    min_delta: float = -0.02,
) -> dict[str, Any]:
    """Compare control vs treatment for a staged rollout and decide the action.

    ``min_delta`` is the worst acceptable quality change before rollback fires.
    """
    if not control_scores or not treatment_scores:
        raise ValueError("control_scores and treatment_scores must be non-empty")

    control_avg = _mean(control_scores)
    treatment_avg = _mean(treatment_scores)
    delta = round(treatment_avg - control_avg, 4)

    if delta < min_delta:
        decision = "rollback"
        stage = "stable"  # all traffic back on the control version
    elif delta >= 0.0:
        decision = "promote"
        stage = "full"
    else:
        decision = "hold"
        stage = "canary"

    return {
        "canary_percent": int(canary_percent),
        "control_avg": control_avg,
        "treatment_avg": treatment_avg,
        "delta": delta,
        "min_delta": float(min_delta),
        "decision": decision,
        "next_stage": stage,
        "rollback_triggered": decision == "rollback",
    }

Here you pass scores for the control (the current version) and the treatment (the new one). The function compares their averages and applies three rules to the difference, called delta:

Delta (treatment minus control)Decision
Lower than min_delta, which defaults to -0.02rollback
Zero or betterpromote
Slightly worse, but not worse than min_deltahold

hold is the useful middle ground: the new version is not clearly bad, so keep it at the canary stage and gather more evidence rather than promote or panic. min_delta is the worst quality loss you are willing to accept, so you set it according to how much risk you can tolerate.

The report also includes rollback_triggered, a plain true or false. If you give it empty score lists it raises an error instead of guessing.

A worked example

This is the demo built into the module, and one of its tests:

  • Control scores: 0.80, 0.82, 0.79, average about 0.8033.
  • Treatment scores: 0.74, 0.71, 0.70, average about 0.7167.
  • The difference is about -0.0866, well under -0.02.
  • The decision is rollback, next_stage is stable, and rollback_triggered is true.

The new version is clearly worse, so it is pulled back before it reaches everyone.

Run it

python -m reliability.r9_release_safety

I ran this and it printed the rollback decision described above. No model is called. Over HTTP, the canary decision is POST /reliability/release/evaluate.

What is simulated, and some honest limits

  • There is no real traffic splitting. canary_percent is only a number that is echoed back. Nothing routes ten percent of users anywhere.
  • The scores are inputs. You supply them; the module does not generate or collect them.
  • It compares plain averages. There is no statistical test, so with only a handful of scores a difference can be pure luck. Real canaries use enough samples to tell signal from noise.
  • Nothing actually rolls back. The module returns a decision for a deployment system to carry out.
  • next_stage names where traffic goes next. promote gives full, hold stays at canary, and rollback gives stable, meaning all traffic goes back to the control version. rollback_triggered is still the plain true/false flag to act on. Nothing in the module moves any traffic; it only reports the stage.
Note

Pair this with R6. R9 decides whether to promote a change using test scores. R6 keeps watching afterwards, so a problem that only shows up later is still caught.

Try it

Try it

1) Make the treatment only slightly worse, for example an average about 0.01 lower, and confirm you get hold. 2) Change min_delta to -0.1 and see how the same data now behaves. 3) Pass identical lists and note that the decision is promote, because a delta of exactly zero counts as no worse. 4) Use shadow_compare with a shadow average 0.03 below live and check that it is not safe to canary.

Common mistakes

  • Promoting on a handful of samples. Averages of three scores are noisy. Gather more before you trust them.
  • Skipping shadow mode. It is the cheapest safety net, because no user sees the result.
  • A canary that is too big. A "small" test that hits half your users is not small.
  • No agreed rollback threshold. Decide min_delta before the test, not after you see the numbers.
  • Releasing and forgetting. Keep monitoring after promotion, as in R6.
  • Changing many things at once. If quality drops you will not know which change caused it.

Check yourself

What is the difference between shadow mode and a canary?

Shadow runs the new version on real inputs but never shows its answers to users, so nobody is affected. A canary serves the new version to a small share of real users, so a bad version can cause limited harm.

When does evaluate_release return hold?

When the new version is slightly worse than the current one, but by less than the allowed min_delta. It is not bad enough to roll back and not good enough to promote.

Why is comparing three average scores a weak basis for a real release decision?

Model output varies, so with so few samples a difference may be luck. Real rollouts need enough samples, and often a statistical test, to be confident.
