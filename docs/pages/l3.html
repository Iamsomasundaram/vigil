Level 3: Routing

The question this level answers: not every CVE deserves the same amount of work, so who decides how much each one gets?

In Level 2 every CVE got the full committee: four specialists and a moderator. That is right for Log4Shell and wasteful for a minor information leak. L3 adds a router at the front. It reads the CVE, picks one of four tracks, and only that track runs.

The idea in plain English

Think of a hospital triage desk. A nurse looks at each arrival and sends them to resuscitation, a normal clinic, a waiting room, or a senior doctor who needs to look first. The nurse does not treat anyone; they only decide where the patient goes.

The four tracks, as defined in the code:

TrackWhen the router picks itWhat runs
critical_responseCVSS 9 or above, or actively exploitedTwo analyses in parallel, then a synthesis call
standard_patchA patch exists, moderate impact, no active exploitationOne focused remediation call
low_risk_monitorLow severity, no known exploits, limited reachOne lightweight summary with a review date
needs_human_reviewNovel, ambiguous or too little public dataA brief for a human analyst. Automation stops here

The key insight: the model as control flow

In ordinary code you write if cvss_score >= 9.0:. That is a lookup table, and it misses nuance. A CVSS 7.5 flaw that attackers are using right now can be more urgent than a CVSS 9.0 that nobody has exploited. A router that reads the description and context can weigh that.

But the model does not run anything. It returns a typed decision, and ordinary Python acts on it. That keeps the dangerous part (running code) deterministic and the fuzzy part (judgement) inside the model.

Part 1: the decision, as a schema

levels/l3_routing.py · RoutingDecision
class RoutingDecision(_Base):
    """Router agent output: which track to run and why."""
    track: Literal[
        "critical_response",  # Actively exploited or CVSS ≥9; run full analysis
        "standard_patch",     # Patch available, moderate impact; focus on remediation
        "low_risk_monitor",   # Low severity, no known exploits; log and review later
        "needs_human_review", # Ambiguous, poorly documented, or novel threat class
    ]
    reason:        str = Field(description="One sentence: why this track was chosen")
    urgency_hours: int = Field(ge=0, description="Estimated hours before action required")
    confidence:    Literal["High", "Medium", "Low"]

The whole level hinges on track. Because it is a Literal of four exact strings, the model cannot answer "kind of critical" or invent a fifth track. Alongside it the router gives a one-sentence reason, an urgency_hours estimate, and a confidence.

Part 2: the router

levels/l3_routing.py · run_router
async def run_router(cve_id: str) -> RoutingDecision:
    """
    Ask the LLM: 'Given this CVE, which response track should we follow?'

    The model reasons about severity, exploitation status, patch availability,
    and affected ecosystem — then returns a structured RoutingDecision.

    Crucially, the `track` field isn't a score or probability; it's a named
    decision that maps directly onto a code path. This makes routing
    deterministic once the LLM has decided.
    """
    payload, usage = await acomplete_json(
        client=client,
        task="route",
        schema_model=RoutingDecision,
        messages=[
            {
                "role": "system",
                "content": (
                    "You are a security triage specialist. Your job is to classify incoming CVEs "
                    "and route them to the correct response track. "
                    "Be decisive — pick the single most appropriate track. "
                    "Prefer 'critical_response' for anything actively exploited in the wild. "
                    "Use 'needs_human_review' only when key facts are genuinely unknown or contradictory."
                ),
            },
            {
                "role": "user",
                "content": (
                    f"Classify this CVE and decide which response track it requires: {cve_id}\n\n"
                    "Tracks:\n"
                    "  critical_response  — CVSS ≥9 OR actively exploited in the wild\n"
                    "  standard_patch     — patch available, moderate impact, no active exploitation\n"
                    "  low_risk_monitor   — CVSS <5, no known exploits, limited blast radius\n"
                    "  needs_human_review — novel, ambiguous, or insufficient public data\n"
                ),
            },
        ],
        temperature=0.1,
        max_tokens=512,
    )
    _usage["prompt_tokens"] += usage.prompt_tokens
    _usage["completion_tokens"] += usage.completion_tokens
    return RoutingDecision.model_validate(payload)

Three things to notice:

  • The system prompt tells the router to be decisive, to prefer critical_response for anything actively exploited, and to use needs_human_review only when key facts are genuinely unknown. That wording shapes how often each track is chosen.
  • The temperature is low (0.1) and the reply is capped at 512 tokens, because a routing decision is short and should be steady.
  • The call goes through acomplete_json from vigil/inference.py, the shared seam that other parts of the project use to talk to model providers. The track handlers below still call the OpenAI client directly.

Part 3: the dispatch table

Instead of a chain of if / elif, the four handlers live in a dictionary:

levels/l3_routing.py · TRACK_HANDLERS
TRACK_HANDLERS = {
    "critical_response":  handle_critical,
    "standard_patch":     handle_standard_patch,
    "low_risk_monitor":   handle_low_risk,
    "needs_human_review": handle_human_review,
}

Adding a fifth track later means writing one handler and adding one line here. Nothing else changes.

Part 4: the pipeline

levels/l3_routing.py · analyse_cve
async def analyse_cve(cve_id: str) -> tuple[RoutingDecision, _Base]:
    """
    Full L3 pipeline: route → dispatch → handle.

    Step 1: Router agent reads the CVE and returns a RoutingDecision.
    Step 2: The track field selects a handler from TRACK_HANDLERS.
    Step 3: The handler runs its specific pipeline and returns a typed report.

    The caller receives both objects so it can display the routing reasoning
    alongside the final report — transparency about why a track was chosen
    is important for trust and auditability.
    """
    _reset_usage()
    console.print("\n[dim]  Running router agent...[/dim]")

    start_router = time.perf_counter()
    routing = await run_router(cve_id)
    router_ms = int((time.perf_counter() - start_router) * 1000)

    console.print(
        f"[dim]  Routed to [bold]{routing.track}[/bold] "
        f"(confidence: {routing.confidence}, {router_ms}ms)[/dim]"
    )
    console.print(f"[dim]  Running {routing.track} handler...[/dim]")

    # ── Key line: LLM output drives Python control flow ────────────────────
    handler = TRACK_HANDLERS[routing.track]    # look up the right function
    result  = await handler(cve_id, routing)   # run it

    return routing, result

Find the two lines that matter:

handler = TRACK_HANDLERS[routing.track]    # look up the right function
result  = await handler(cve_id, routing)   # run it

That is "the LLM's output drives Python control flow" in two lines. The function returns both the routing decision and the track's result, so a user can see why a track was chosen alongside what it found. Transparency about the reasoning is what makes the decision auditable.

Notice too that each handler receives routing, and uses routing.reason in its own prompt. The specialist is told why it was chosen, so it does not redo the triage.

The critical track reuses Level 2

levels/l3_routing.py · handle_critical
async def handle_critical(cve_id: str, routing: RoutingDecision) -> CriticalReport:
    """
    Critical track: runs two agents in parallel (mirroring L2's fan-out),
    then asks a synthesis agent to produce actionable output.

    We fan out exploitability + impact simultaneously, then a third call
    synthesises them into a CriticalReport. Total latency ≈ max(call1, call2) + call3.
    """

    # ── Sub-agent 1: Exploitability ───────────────────────────────────────────
    async def _exploitability() -> str:
        r = await client.chat.completions.create(
            model=MODEL,
            messages=[
                {"role": "system", "content": "You are a penetration tester. Assess exploitability."},
                {"role": "user",   "content": f"How easy is {cve_id} to exploit? Any public PoC or active exploitation?"},
            ],
            temperature=0.1,
            max_tokens=400,
        )
        _track(r)
        return r.choices[0].message.content

    # ── Sub-agent 2: Impact ───────────────────────────────────────────────────
    async def _impact() -> str:
        r = await client.chat.completions.create(
            model=MODEL,
            messages=[
                {"role": "system", "content": "You are a security architect. Assess blast radius and CIA triad impact."},
                {"role": "user",   "content": f"If {cve_id} is exploited, what breaks? How widely?"},
            ],
            temperature=0.1,
            max_tokens=400,
        )
        _track(r)
        return r.choices[0].message.content

    # Run both sub-agents in parallel — L2's asyncio.gather() pattern applied here
    exploitability_text, impact_text = await asyncio.gather(_exploitability(), _impact())

    # ── Synthesis: combine both analyses into a structured CriticalReport ─────
    response = await client.chat.completions.create(
        model=MODEL,
        messages=[
            {
                "role": "system",
                "content": (
                    "You are a security incident commander. Synthesise the specialist findings "
                    "into a clear, actionable critical response report."
                ),
            },
            {
                "role": "user",
                "content": (
                    f"CVE: {cve_id}\n"
                    f"Router classification: {routing.reason}\n\n"
                    f"Exploitability analysis:\n{exploitability_text}\n\n"
                    f"Impact analysis:\n{impact_text}\n\n"
                    "Produce the critical response report."
                ),
            },
        ],
        response_format={
            "type": "json_schema",
            "json_schema": {
                "name":   "CriticalReport",
                "strict": True,
                "schema": _strict_schema(CriticalReport),
            },
        },
        temperature=0.1,
        max_tokens=2048,
    )
    _track(response)
    return CriticalReport.model_validate(
        json.loads(response.choices[0].message.content)
    )

Read the comments in the function: it runs exploitability and impact in parallel with asyncio.gather (the same trick as L2), then makes a third call to synthesise a CriticalReport. The cheap tracks make one call. Routing is how the expensive pattern is kept for the threats that deserve it.

The safety valve: human review

levels/l3_routing.py · handle_human_review
async def handle_human_review(cve_id: str, routing: RoutingDecision) -> HumanReviewFlag:
    """
    Human review track: automation stops here.
    The output is a structured brief for a human analyst — not a final decision.

    This is an important safety pattern: when the AI is uncertain, it doesn't
    guess and act. It escalates with a clear explanation of what it knows and
    what questions need human judgement.
    """
    response = await client.chat.completions.create(
        model=MODEL,
        messages=[
            {
                "role": "system",
                "content": (
                    "You are a security triage coordinator. "
                    "This CVE requires human review before any automated action. "
                    "Prepare a clear brief for the analyst."
                ),
            },
            {
                "role": "user",
                "content": (
                    f"CVE: {cve_id}\n"
                    f"Reason flagged for review: {routing.reason}\n\n"
                    "List what is known, what is uncertain, and what questions the analyst must answer."
                ),
            },
        ],
        response_format={
            "type": "json_schema",
            "json_schema": {
                "name":   "HumanReviewFlag",
                "strict": True,
                "schema": _strict_schema(HumanReviewFlag),
            },
        },
        temperature=0.2,   # Slightly higher — we want the questions to be varied and thorough
        max_tokens=1024,
    )
    _track(response)
    return HumanReviewFlag.model_validate(
        json.loads(response.choices[0].message.content)
    )

This handler does not decide anything. Its output is a brief: what is known, what is uncertain, and the questions a person must answer. This is an important safety pattern. When the model is unsure, it escalates instead of guessing and acting.

Run it

python levels/l3_routing.py CVE-2021-44228
python levels/l3_routing.py CVE-2014-0160

The command prints a line saying the router is running, then which track it chose with its confidence, then a Router Decision panel (track, reason, act-within hours, confidence), and finally an analysis panel whose layout depends on the track. Try a famous critical CVE and a less well-known one and compare which tracks they land in. I have not captured sample output here, because the choice is the model's and can vary between runs.

Warning

The router is an LLM, so it can mis-route. A wrong low_risk_monitor on a dangerous CVE is worse than a wasted full analysis. That is why a confidence field and a human-review track exist, and why later reliability work (R2 evaluation) measures routing quality against known answers.

Try it

Try it

1) Run the same CVE three times and note whether the track ever changes. 2) Edit the router's system prompt to say "Prefer standard_patch whenever a patch exists" and see which CVEs move. 3) Add a fifth track, for example vendor_followup: add a value to the Literal, a handler function, and one line in TRACK_HANDLERS.

Common mistakes

  • Trusting the router blindly. It is one model's judgement. Log its reason and confidence, and measure it.
  • Letting the model run code. The model only chooses a name. Your dictionary decides what that name does.
  • Too many tracks. Each one needs a handler and tests. Start with a few that are clearly different.
  • No escape hatch. A router with no "I don't know" route will force a guess. Keep a human-review track.
  • Forgetting the router's own cost. Routing adds one call to every CVE. It pays off only when it saves more than it costs.

Check yourself

Why does the router return a Literal track instead of free text?

Free text would need parsing and could contain surprises. A Literal guarantees one of four exact values, so a dictionary lookup is always safe.

What is the difference between the router and a track handler?

The router only decides where a CVE goes. The handler does the actual analysis for that track.

Why does the needs_human_review handler produce questions instead of a verdict?

It is the case where automation is least trustworthy. Escalating with a clear brief is safer than a confident guess.

How does L3 reuse L2?

The critical track runs two analyses in parallel with asyncio.gather, the same fan-out idea as L2.
