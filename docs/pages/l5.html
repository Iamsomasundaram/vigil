Level 5: Memory

The question this level answers: how does the system know what it already did, and what happened next?

Every level so far starts from a blank slate. Ask about the same CVE on day 1 and on day 60 and the model has no idea it ever saw it, whether you patched it, or whether the risk changed. L5 gives the system a memory, and a way to learn from outcomes.

The idea in plain English

A model does not remember anything between calls (see How LLMs work). So "memory" is not something inside the model. It is your code saving results to a database, then pasting the relevant history into the next prompt. The model reads that history like any other text.

Recallread history from the database
→
Analysetool loop + that history
→
Remembersave the new result

Then, later, a person tells the system what happened (patched, dismissed...). That feedback is stored too, so the next run can see it.

Three kinds of memory

The comment at the top of levels/l5_memory.py names three ideas:

KindPlain meaningWhere it lives
Episodic"What we did": each past analysisthe analyses table
Feedback"What happened": patched, dismissed, in progress...the feedback table
Similar incidents"What looks like this one"the analysis_vectors table

The third one is covered in its own section below. The "trend awareness" idea in the file's header comment is mostly left to the model: the history it receives includes earlier CVSS and EPSS values, and the prompt tells it to note changes. There is no separate code that computes trends.

Why a database?

A Python dictionary disappears when the program stops. A database keeps data across restarts and lets you query it. Vigil uses PostgreSQL, accessed with asyncpg and plain SQL so you can see exactly what runs. The schema is created on first use by init_db, which is safe to run repeatedly because every statement says IF NOT EXISTS:

levels/l5_memory.py · init_db
async def init_db(conn: asyncpg.Connection) -> None:
    """
    Create tables if they don't exist.

    Called once at startup. Safe to call multiple times (IF NOT EXISTS).

    Schema design:
      analyses  — one row per analysis run, result stored as JSONB
      feedback  — one row per feedback submission, linked to a specific analysis
    """
    await conn.execute("""
        CREATE TABLE IF NOT EXISTS analyses (
            id          SERIAL PRIMARY KEY,
            cve_id      TEXT        NOT NULL,
            level       INTEGER     NOT NULL DEFAULT 5,
            result      JSONB       NOT NULL,
            tool_calls  JSONB,
            created_at  TIMESTAMPTZ NOT NULL DEFAULT NOW()
        )
    """)
    await conn.execute("""
        CREATE TABLE IF NOT EXISTS feedback (
            id           SERIAL PRIMARY KEY,
            cve_id       TEXT        NOT NULL,
            analysis_id  INTEGER     REFERENCES analyses(id),
            status       TEXT        NOT NULL,
            notes        TEXT        NOT NULL DEFAULT '',
            created_at   TIMESTAMPTZ NOT NULL DEFAULT NOW()
        )
    """)
    # Index on cve_id so history lookups are fast even with thousands of entries
    await conn.execute("""
        CREATE INDEX IF NOT EXISTS idx_analyses_cve_id  ON analyses(cve_id)
    """)
    await conn.execute("""
        CREATE INDEX IF NOT EXISTS idx_feedback_cve_id  ON feedback(cve_id)
    """)
    await conn.execute("""
        CREATE TABLE IF NOT EXISTS analysis_vectors (
            analysis_id INTEGER PRIMARY KEY REFERENCES analyses(id) ON DELETE CASCADE,
            cve_id      TEXT NOT NULL,
            summary     TEXT NOT NULL,
            embedding   JSONB NOT NULL,
            created_at  TIMESTAMPTZ NOT NULL DEFAULT NOW()
        )
    """)
    await conn.execute("""
        CREATE INDEX IF NOT EXISTS idx_analysis_vectors_cve_id ON analysis_vectors(cve_id)
    """)

Two details to notice. The analysis itself is stored in a JSONB column, a flexible structured field, so the table does not need a column per result field. And feedback points at an analysis through analysis_id.

Step 1: Recall

Reading history is a normal SQL query. get_history returns the most recent analyses for a CVE, newest first, with the latest feedback attached to each:

levels/l5_memory.py · get_history
async def get_history(
    conn:   asyncpg.Connection,
    cve_id: str,
    limit:  int = 5,
) -> list[dict]:
    """
    Retrieve the most recent analyses for a CVE, newest first.

    We limit to 5 to keep the injected memory context manageable.
    Too much history would crowd the model's context window.
    """
    rows = await conn.fetch(
        """
        SELECT
            a.id,
            a.created_at,
            a.result,
            f.status  AS feedback_status,
            f.notes   AS feedback_notes
        FROM analyses a
        LEFT JOIN LATERAL (
            -- Most recent feedback for each analysis
            SELECT status, notes
            FROM feedback f2
            WHERE f2.analysis_id = a.id
            ORDER BY f2.created_at DESC
            LIMIT 1
        ) f ON true
        WHERE a.cve_id = $1
        ORDER BY a.created_at DESC
        LIMIT $2
        """,
        cve_id,
        limit,
    )
    return [dict(row) for row in rows]

It defaults to the latest 5 runs. The comment in the code gives the reason: too much history would crowd the model's context window.

Step 2: Turn history into prompt text

Rows are not a prompt. build_memory_context formats them into a readable block, and that block is pasted into the system prompt inside run_memory_aware_loop:

levels/l5_memory.py · build_memory_context
def build_memory_context(history: list[dict]) -> str:
    """
    Convert database rows into a human-readable (and model-readable) context string.

    This text is injected into the agent's system prompt so the model
    knows what has happened before it begins its current analysis.

    Format matters: the model reads this, so we want it structured and concise.
    Too verbose and it crowds out room for tool results. Too terse and the model
    misses important context.
    """
    if not history:
        return "No prior analyses found for this CVE."

    lines = [f"ANALYSIS HISTORY ({len(history)} prior run(s), newest first):", ""]
    for entry in history:
        lines.append(_format_history_entry(entry))
        lines.append("")

    return "\n".join(lines)

This technique is called in-context learning, the simplest kind of memory: the model is not retrained, it just reads more text. The system prompt also tells the model what to do with the text: note changes since last time, reference any feedback, and set memory_context_used and notable_change in its answer.

The analysis itself is the same tool loop you met in L4, with a limit of 10 iterations, calling the NVD and EPSS tools and then producing a structured result. The new output class adds memory fields such as first_seen, times_analysed and notable_change:

levels/l5_memory.py · MemoryAwareAnalysis
class MemoryAwareAnalysis(_Base):
    """
    Final analysis from the memory-aware agent.

    Extends L4's GroundedAnalysis with memory-specific fields that only
    make sense when history exists:
      - first_seen: when this CVE first appeared in our records
      - times_analysed: how many times we've examined this CVE
      - status_changed: did the risk picture change since last analysis?
      - memory_context_used: did past history influence this recommendation?
    """
    cve_id:               str
    cvss_score:           float
    cvss_severity:        str
    epss_score:           float   = Field(ge=0.0, le=1.0)
    epss_percentile:      float   = Field(ge=0.0, le=1.0)
    recommended_action:   str
    patch_available:      bool
    # Memory-specific fields
    first_seen:           str     = Field(description="ISO date of first analysis, or 'first_time' if new")
    times_analysed:       int     = Field(ge=0, description="Total prior analyses including this one")
    memory_context_used:  bool    = Field(description="True if past history influenced this recommendation")
    notable_change:       str     = Field(description="What changed since last analysis, or 'First analysis'")
    data_sources:         list[str]

Step 3: Remember, and let the database correct the model

After the analysis, analyse_cve saves the result. One line deserves attention:

analysis_dict["times_analysed"] = len(history) + 1

The model is asked to fill in times_analysed, but it can only guess. The database knows the real count, so the code overwrites the model's number before saving. That is a good habit: let the model write, and let your code own the facts it can compute exactly.

Here is the whole pipeline:

levels/l5_memory.py · analyse_cve
async def analyse_cve(
    cve_id: str,
    db_url: str = DB_URL,
) -> tuple[MemoryAwareAnalysis, list[dict], list[dict], ContextBudgetReport]:
    """
    Full L5 pipeline: recall → analyse → remember.

    Step 1 — RECALL:   query DB for prior analyses of this CVE
    Step 2 — ANALYSE:  run tool loop with memory injected into system prompt
    Step 3 — REMEMBER: persist the new analysis for future runs

    Returns (analysis, tool_call_log, history, context_budget) so callers can see
    what the agent did, what it remembered, and how memory was fit to the budget.
    """
    _reset_usage()
    conn = await asyncpg.connect(db_url)
    try:
        # Ensure schema exists (idempotent — safe to call every time)
        await init_db(conn)

        # ── Step 1: RECALL ─────────────────────────────────────────────────
        console.print(f"\n[dim]  Checking memory for {cve_id}...[/dim]")
        history = await get_history(conn, cve_id)
        semantic_matches = await semantic_recall(conn, cve_id, k=5, threshold=0.55)
        memory_block, context_budget = await build_budgeted_memory_context(history)
        memory_context = (
            memory_block
            + "\n\n"
            + build_semantic_context(semantic_matches)
        )

        if history:
            console.print(f"[dim]  Found {len(history)} prior analysis/analyses in memory[/dim]")
            if context_budget.was_summarized:
                console.print(f"[dim]  Older history summarized to fit {context_budget.budget_tokens}-token budget[/dim]")
        else:
            console.print("[dim]  No prior history — first analysis for this CVE[/dim]")

        # ── Step 2: ANALYSE ────────────────────────────────────────────────
        console.print("[dim]  Running memory-aware tool loop...[/dim]")
        analysis, tool_log = await run_memory_aware_loop(cve_id, memory_context)

        # ── Step 3: REMEMBER ───────────────────────────────────────────────
        # Overwrite the times_analysed field to reflect the real count
        # (the model guesses, but the DB knows exactly).
        # We rebuild the model from the corrected dict so the RETURNED object
        # matches what was persisted — callers see the canonical count, not the
        # model's guess.
        analysis_dict = analysis.model_dump()
        analysis_dict["times_analysed"] = len(history) + 1

        row_id = await save_analysis(conn, cve_id, analysis_dict, tool_log)
        summary = _summary_for_embedding(analysis_dict)
        await save_semantic_vector(conn, row_id, cve_id, summary, await embed_text(summary))
        console.print("[dim]  Analysis saved to memory[/dim]")

        # Return the corrected model, not the original stale object
        corrected = type(analysis).model_validate(analysis_dict)
        return corrected, tool_log, history, context_budget

    finally:
        await conn.close()

Feedback: closing the loop

Memory of what the agent said is only half the story. The valuable signal is what happened. record_feedback stores an outcome against the most recent analysis for that CVE. The status values listed in the code are patched, dismissed, in_progress, still_vulnerable and monitoring.

Next time the CVE is analysed, get_history joins the latest feedback onto each run, and the formatter prints a line such as Feedback: PATCHED into the history the model reads.

Memory can grow: the token budget

History grows without limit, but a model's context window does not. build_budgeted_memory_context keeps the injected memory under a token budget, and it explains its priority in its docstring:

  1. If everything fits, use it all verbatim.
  2. Otherwise keep the most recent few runs verbatim and ask the model to summarise the older ones.
  3. If that is still too long, drop the summary and then drop the oldest verbatim runs.

It also returns a small report saying how many entries were verbatim, how many were summarised, and whether anything was truncated. Two settings control it, both in .env.example:

SettingWhat it doesDefault in the code
VIGIL_MEMORY_TOKEN_BUDGETMaximum tokens of memory injected1500
VIGIL_MEMORY_RECENT_VERBATIMHow many recent runs are always kept word-for-word2

Token counts use tiktoken when it is installed, and otherwise a rough "about four characters per token" guess, so the project still runs offline. Summarising older entries costs an extra model call, which is one reason the budget exists.

Similar incidents: semantic recall

get_history only finds runs of the same CVE. L5 also finds other CVEs whose stored summaries look similar, using embeddings: lists of numbers that represent text, where similar texts end up close together.

The flow is: after each analysis, a short summary of the result is embedded and saved in analysis_vectors. On the next run, semantic_recall compares the current CVE's summary with the stored ones using cosine similarity and returns the closest matches above a threshold (0.55 by default, up to 5 results). Those matches are added to the prompt as "relevant prior incidents", with a line telling the model to treat them as data, not instructions.

The embedding method is chosen by VIGIL_EMBED_MODE:

ModeWhat it isHonest limitation
local (the default)A small deterministic hash-based vector (32 numbers), no networkIt only reflects word overlap. The code comment says outright that it is not semantic.
openaiReal embeddings from text-embedding-3-small (1536 numbers)Needs a working API key. On any error the code falls back to the local method instead of crashing.

So with the default setting, "similar incidents" means "summaries sharing many of the same words". To see genuinely meaning-based matches, switch to openai mode. Embeddings and retrieval are explored further in Retrieval, and caching ideas in Semantic caching.

Note

Only recent vectors are searched: the query reads the latest 200 stored rows. That is fine for learning, and one of the first things to change at scale.

Setting up PostgreSQL

L5 and L6 will not run without a database. You have two routes.

Route A: Docker Compose (simplest). From the repository root:

docker compose up --build

This starts the API, a PostgreSQL 16 container and Redis, plus the web interface. The Compose file publishes PostgreSQL on port 5432, with the user, password and database all set to vigil.

Route B: your own PostgreSQL. Create a database and point DATABASE_URL at it in .env.

About the connection string, which is easy to get wrong:

  • The level scripts default to postgresql://vigil:vigil@localhost:5432/vigil. That works from your own terminal when the Compose database is running, because the port is published to your machine.
  • The API's endpoints default to the same user and password but with host db. That name only resolves inside the Compose network. If you run the API locally outside Docker, set DATABASE_URL yourself.
Warning

vigil:vigil is a throwaway learning password. Never reuse it anywhere real.

Run it

With the database up and your API key set:

python levels/l5_memory.py CVE-2021-44228
python levels/l5_memory.py CVE-2021-44228
python levels/l5_memory.py CVE-2021-44228 --feedback patched --notes "Upgraded the library"
python levels/l5_memory.py CVE-2021-44228

What the code is designed to do on each run:

  1. First run: it reports no prior history, analyses the CVE with live tools, and saves the result.
  2. Second run: it finds one earlier analysis, shows it in an "Organisation Memory" panel, and passes it to the model.
  3. Feedback run: it records the outcome and exits without analysing.
  4. Third run: the history now carries the feedback line, so the model can take it into account.

After each analysis the script prints a context-budget line showing tokens used out of the budget and how many entries were verbatim or summarised. Check that the "Times analysed" figure goes up by one on each analysis run; that number comes from the database count, not from the model.

The same functions are exposed by the API as POST /l5/analyse, POST /l5/feedback, GET /l5/history/{cve_id} and GET /l5/similar/{cve_id}, and the web interface has a page for L5.

Try it

Try it

1) Run the analysis twice, then query the analyses table with any PostgreSQL client and look at the JSONB result column. 2) Set VIGIL_MEMORY_TOKEN_BUDGET very low (for example 200) and re-run after a few analyses: does the budget line report summarising or truncation? 3) Analyse two different CVEs, then call GET /l5/similar/{cve_id} in local mode and then openai mode, and compare which matches appear. 4) Record dismissed feedback with a note and see whether the next analysis mentions it.

Common mistakes

  • Thinking the model "remembers". It only sees what you paste into the prompt. If history is not injected, it is not known.
  • Injecting everything. More history costs more tokens and can drown out the fresh tool data. Budget it.
  • Trusting the model's counts. Compute facts such as "how many times" in code.
  • Treating local embeddings as semantic. In the default mode they match shared words, not meaning.
  • Treating stored history as instructions. Memory is text from the past. The code labels semantic matches as data, and you should keep it that way, because anything stored can influence a later prompt.
  • Forgetting the database is stateful. Re-running tests or demos against a shared database mixes old and new history. Use a throwaway database for experiments.
  • No privacy plan. Stored analyses persist indefinitely. See Privacy before storing anything sensitive.

Check yourself

Where does the "memory" of an LLM application actually live?

In your own storage, here PostgreSQL, not in the model. Code reads the history and adds it to the prompt on each call.

Why does the code overwrite times_analysed after the model answers?

The model can only guess the count, while the database knows it exactly. Facts your code can compute should not be left to the model.

What happens when the memory is too big for its token budget?

Recent runs are kept verbatim, older ones are summarised, and if that still overflows the summary and then the oldest verbatim runs are dropped. If one run alone is bigger than the whole budget, it is cut down to fit, so the budget is a hard ceiling. A report records what was done.

Why does feedback matter more than the analyses themselves?

It records what actually happened after the advice, which is the only way the system can tell whether it was followed or useful.

In the default embedding mode, why are "similar incidents" not truly similar in meaning?

The local method hashes words into a small vector, so it reflects word overlap only. Real semantic matching needs the openai embedding mode.
