Foundations

Retrieval and RAG

The question this page answers: how do I give a model the right facts to answer from, instead of trusting its memory?

In Level 0 the model answered from what it learned in training, which can be out of date or wrong. Retrieval-augmented generation (RAG) fixes that in two moves: first retrieve the most relevant passages from your own documents, then hand them to the model along with the question so it answers from them.

Question
→
Retrievefind the best passages
→
Promptquestion + passages
→
Model
→
Answer

Most RAG failures are not model failures. They are retrieval failures: the right passage was never found, so the model never saw it. This page is about making retrieval good and measuring whether it is.

Note

The code in levels/foundations/retrieval_quality.py is deliberately small and runs offline with no API key. Its scoring is word matching, not real semantic search. Read the sections below to see exactly what is simplified.

Step 1: Chunking

Documents are too long to search or send whole, so they are cut into chunks. Chunk size is a real trade-off:

  • Small chunks are precise but may lose surrounding context.
  • Large chunks keep context but dilute the match and cost more tokens when sent to the model.

Vigil cuts by words, with an overlap so a sentence on a boundary appears in two chunks:

levels/foundations/retrieval_quality.py · chunk_text
def chunk_text(text: str, *, chunk_size_words: int = 80, overlap_words: int = 20) -> list[str]:
    """Chunk text with fixed word windows and overlap."""
    words = text.split()
    if not words:
        return []

    chunk_size_words = max(20, int(chunk_size_words))
    overlap_words = max(0, int(overlap_words))
    if overlap_words >= chunk_size_words:
        overlap_words = max(0, chunk_size_words - 1)

    step = max(1, chunk_size_words - overlap_words)
    chunks: list[str] = []
    for start in range(0, len(words), step):
        end = min(len(words), start + chunk_size_words)
        piece = " ".join(words[start:end]).strip()
        if piece:
            chunks.append(piece)
        if end >= len(words):
            break
    return chunks

Two details worth noticing: the chunk size is never allowed below 20 words, and the overlap is forced to be smaller than the chunk so the window always moves forward.

Step 2: Scoring (lexical retrieval)

Each chunk is reduced to the set of its non-trivial words. A query is scored against a chunk by how many query words it contains:

levels/foundations/retrieval_quality.py · _score
def _score(query_terms: set[str], chunk_terms: set[str]) -> tuple[float, int, list[str]]:
    if not query_terms:
        return 0.0, 0, []
    overlap = sorted(query_terms.intersection(chunk_terms))
    overlap_count = len(overlap)
    if overlap_count == 0:
        return 0.0, 0, []

    coverage = overlap_count / max(1, len(query_terms))
    density = overlap_count / max(1, len(chunk_terms))
    score = (0.75 * coverage) + (0.25 * density)
    return score, overlap_count, overlap
  • Coverage is the share of query words found in the chunk. It carries 75% of the score.
  • Density is the share of the chunk's words that matched. It carries 25%, and slightly favours tighter chunks.

retrieve scores every chunk and returns the best top_k:

levels/foundations/retrieval_quality.py · retrieve
def retrieve(
    query: str,
    index: list[dict[str, Any]],
    *,
    top_k: int = 5,
    min_score: float = 0.01,
) -> list[dict[str, Any]]:
    """Run lexical retrieval over a chunk index."""
    q_terms = set(_query_terms(query))
    rows: list[dict[str, Any]] = []

    for chunk in index:
        score, overlap_count, overlap_terms = _score(q_terms, chunk.get("terms", set()))
        if score < min_score:
            continue
        rows.append(
            {
                "chunk_id": chunk["chunk_id"],
                "doc_id": chunk["doc_id"],
                "title": chunk["title"],
                "score": round(score, 4),
                "overlap_count": overlap_count,
                "overlap_terms": overlap_terms,
                "word_count": chunk.get("word_count", 0),
                "text_preview": (chunk["text"][:160] + "...") if len(chunk["text"]) > 160 else chunk["text"],
            }
        )

    rows.sort(key=lambda r: (r["score"], r["overlap_count"]), reverse=True)
    return rows[: max(1, int(top_k))]

What this simple scorer cannot do

It matches exact words only. There is no stemming and no synonyms. Try the default query log4j remote code execution patch against the built-in Log4j advisory: the advisory says "patched", not "patch", so the word patch does not match, and the chunk scores on the other four words.

This is the same weakness real keyword search has, and it is why the next two steps exist.

Step 3: Measuring retrieval

"It looks right" is not a measurement. To compare two settings you need a labelled set: queries, plus the documents that should be found. Vigil ships one in data/eval/retrieval_golden.json, where each row looks like this:

{"query": "log4j remote code execution patch", "relevant_doc_ids": ["doc1"]}

Three standard metrics score a ranked list against those labels. Each takes the retrieved document ids and the relevant ones:

levels/foundations/retrieval_quality.py · recall_at_k
def recall_at_k(retrieved_doc_ids: list[str], relevant_doc_ids: list[str], k: int) -> float:
    """Recall@k over document ids (not chunk ids)."""
    rel = set(relevant_doc_ids)
    if not rel:
        return 0.0
    top = set(retrieved_doc_ids[: max(1, int(k))])
    return len(rel.intersection(top)) / len(rel)
levels/foundations/retrieval_quality.py · reciprocal_rank
def reciprocal_rank(retrieved_doc_ids: list[str], relevant_doc_ids: list[str], k: int) -> float:
    """Reciprocal rank of the first relevant item in top-k."""
    rel = set(relevant_doc_ids)
    for i, doc_id in enumerate(retrieved_doc_ids[: max(1, int(k))], 1):
        if doc_id in rel:
            return 1.0 / i
    return 0.0
levels/foundations/retrieval_quality.py · ndcg_at_k
def ndcg_at_k(retrieved_doc_ids: list[str], relevant_doc_ids: list[str], k: int) -> float:
    """nDCG@k for binary relevance."""
    k_eff = max(1, int(k))
    rel = set(relevant_doc_ids)
    observed = [1 if d in rel else 0 for d in retrieved_doc_ids[:k_eff]]
    ideal = [1] * min(len(rel), k_eff) + [0] * max(0, k_eff - len(rel))
    denom = _dcg(ideal)
    if denom == 0.0:
        return 0.0
    return _dcg(observed) / denom
MetricQuestion it answersRange
Recall@kOf the documents I needed, how many appeared in the top k?0 to 1
MRR (mean reciprocal rank)How near the top was the first relevant result? 1st gives 1.0, 2nd gives 0.5, 3rd about 0.330 to 1
nDCG@kAre the relevant results ranked above the irrelevant ones?0 to 1

evaluate_retrieval_settings runs two chunking configurations over the whole labelled set and reports the averages for each, a winner and the differences.

Warning

On the built-in sample, all three documents are only about 23 words long, so each becomes a single chunk whatever size you choose. Comparing chunk sizes there gives a tie, and that is correct, not a bug. Chunk-size experiments only mean something on longer documents. Add your own longer texts through the documents argument.

Step 4: Hybrid retrieval and reranking

Real systems rarely rely on one signal. Vigil's hybrid lab blends two:

  • a lexical score (word overlap, as above), and
  • a vector score, from turning text into a list of numbers and comparing them with cosine similarity.

The two are normalised to the same scale and mixed with a weight alpha, where 1.0 means pure lexical:

levels/foundations/retrieval_quality.py · hybrid_retrieve
def hybrid_retrieve(
    query: str,
    index: list[dict[str, Any]],
    *,
    mode: str = "hybrid",
    alpha: float = 0.5,
    rerank: bool = False,
    top_k: int = 5,
) -> list[dict[str, Any]]:
    """Retrieve with lexical, vector, or fused hybrid scoring, optional rerank.

    ``alpha`` weights lexical vs vector in hybrid mode (1.0 = pure lexical).
    """
    q_terms = set(_query_terms(query))
    lex = _normalize(_lexical_scores(q_terms, index))
    vec = _normalize(_vector_scores(q_terms, index))

    fused: dict[str, float] = {}
    for chunk in index:
        cid = chunk["chunk_id"]
        if mode == "lexical":
            fused[cid] = lex.get(cid, 0.0)
        elif mode == "vector":
            fused[cid] = vec.get(cid, 0.0)
        else:
            fused[cid] = alpha * lex.get(cid, 0.0) + (1.0 - alpha) * vec.get(cid, 0.0)

    by_id = {c["chunk_id"]: c for c in index}
    rows: list[dict[str, Any]] = []
    for cid, base in fused.items():
        chunk = by_id[cid]
        rerank_score = _rerank(q_terms, chunk) if rerank else None
        final = rerank_score if rerank else base
        rows.append(
            {
                "chunk_id": cid,
                "doc_id": chunk["doc_id"],
                "title": chunk["title"],
                "mode": mode,
                "lexical_score": round(lex.get(cid, 0.0), 4),
                "vector_score": round(vec.get(cid, 0.0), 4),
                "fused_score": round(base, 4),
                "rerank_score": round(rerank_score, 4) if rerank_score is not None else None,
                "score": round(final, 4),
                "text_preview": (chunk["text"][:160] + "...") if len(chunk["text"]) > 160 else chunk["text"],
            }
        )

    rows.sort(key=lambda r: r["score"], reverse=True)
    return rows[: max(1, int(top_k))]

An optional rerank step then re-scores the shortlist with a stricter check, rewarding chunks that contain the query words and have them early:

levels/foundations/retrieval_quality.py · _rerank
def _rerank(query_terms: set[str], chunk: dict[str, Any]) -> float:
    """Lightweight cross-encoder proxy: reward exact-term coverage + phrase overlap."""
    chunk_terms = chunk.get("terms", set())
    if not query_terms or not chunk_terms:
        return 0.0
    overlap = query_terms.intersection(chunk_terms)
    coverage = len(overlap) / max(1, len(query_terms))
    early = 0.0
    words = chunk.get("text", "").lower().split()
    head = set(words[:30])
    early = len(query_terms.intersection(head)) / max(1, len(query_terms))
    return round(0.6 * coverage + 0.4 * early, 6)

The honest caveat about the "vector" score

The vector here comes from _hash_embed:

levels/foundations/retrieval_quality.py · _hash_embed
def _hash_embed(terms: set[str], dims: int = 64) -> list[float]:
    """Deterministic offline embedding: hash terms into a fixed vector."""
    vec = [0.0] * dims
    for t in terms:
        h = 0
        for ch in t:
            h = (h * 131 + ord(ch)) & 0xFFFFFFFF
        vec[h % dims] += 1.0
    norm = math.sqrt(sum(v * v for v in vec))
    if norm == 0.0:
        return vec
    return [v / norm for v in vec]

It hashes each word into one of 64 buckets and counts. That is a teaching stand-in, not a real embedding. It has no idea that "arbitrary code execution" and "remote code execution" mean nearly the same thing. It also lets unrelated text score above zero when words happen to land in the same bucket: for the query arbitrary code execution in log4j, the unrelated HTTP/2 note gets a non-zero vector score while its lexical score is zero.

A real embedding model maps meaning to nearby points, so paraphrases score high even with no shared words. Vigil supports that in L5 memory by setting VIGIL_EMBED_MODE=openai, which uses text-embedding-3-small. The notebook notebooks/03_embeddings_rag.ipynb walks through local versus real embeddings. Rerunning the lab with real embeddings would give different, better semantic results; the code here does not do that.

Common mistakes

  • Judging by eye. Build a small labelled set and use Recall, MRR and nDCG.
  • Tuning on three examples. A tiny benchmark tells you almost nothing; it only proves the mechanics.
  • Chunks too large. The relevant sentence is buried and you pay for the extra tokens.
  • Chunks too small. The passage loses the context that made it meaningful.
  • Assuming the vector score means semantic. Here it does not; it is a hash.
  • Blaming the model. If the right passage was not retrieved, no prompt can fix the answer.

Check yourself

Why does overlap between chunks help?

A fact that sits on a chunk boundary would otherwise be cut in half. Overlap keeps it whole in at least one chunk.

A query uses the word "patch" but the document says "patched". What happens in Vigil's lexical search, and why?

That word does not match, because matching is on exact words with no stemming. The chunk can still match on other words, but its score is lower.

What does MRR reward that Recall@k does not?

Where the first relevant result appears. Recall@k only checks whether it is in the top k; MRR rewards ranking it first.

Why is Vigil's built-in vector score not real semantic search?

It hashes words into buckets instead of using a trained embedding model, so it cannot see that different words mean the same thing.
