Level 6: Autonomous agent

The question this level answers: what changes when the system acts without waiting for you?

In L0 to L5 a person always starts the run: you ask, the system answers. L6 flips that. You add CVEs to a watchlist once. After that a background loop checks them on a schedule, notices when something matters, and leaves an alert for you to review.

Automated versus autonomous

The file's own header draws the line, and it is worth remembering:

Who starts the work?Example
Automated (L1 to L5)A person or a triggerYou run a level and read the result
Autonomous (L6)The system, on its own scheduleThe loop scans the watchlist every interval

The test is simple: does the system initiate action, or only respond to it?

The idea in plain English

Imagine a night-shift analyst with a list of CVEs. Every hour they check the latest numbers, compare them with their notes from last time, and write a note only if something meaningfully changed. When you arrive, the notes are waiting.

Read watchlist
→
Fetch live dataNVD + EPSS
→
Compare with last state
→
Meaningful change?rules in code
→
Write alertthen wait for a human

L6 reuses the earlier levels

L6 is built from pieces you have already met:

Earlier levelHow L6 uses it
L2, parallel fan-outasyncio.gather fetches NVD and EPSS together, and scans many CVEs at once
L4, toolsThe same NVD and EPSS data sources, but called as plain functions, not through a model's tool loop
L5, memoryA scan_state table remembers the last known numbers per CVE, so there is something to compare against
Note

The header comment of the file also says L3 routing decides each alert's severity. In the code that decision is a small lookup table, not the L3 routing step. Read the code, not the comment, when they differ.

The most important design choice: rules decide, the model words

Here is the key idea of this level. Deciding that something changed is done in plain Python, not by the model. Only the writing of the alert is done by the model.

levels/l6_autonomous.py · detect_changes
def detect_changes(
    cve_id:      str,
    last_state:  dict | None,
    current_nvd: dict,
    current_epss: float,
) -> ChangeSignal:
    """
    Compare current data against the last known state and classify the change.

    This is a deterministic function — no LLM involved. The thresholds are
    explicit rules. The LLM is called AFTER this to generate human-readable
    alert text, but the decision of WHAT changed is made here, in code.

    Why deterministic change detection instead of asking the LLM?
      Reliability. An LLM might interpret "0.01 → 0.02" as significant
      on one run and insignificant on another. Code is consistent.
      The LLM's job is to communicate the finding well, not to make it.
    """
    prev_epss = last_state["epss_score"] if last_state else 0.0
    prev_cvss = last_state["cvss_score"] if last_state else 0.0
    prev_patch = last_state["patch_known"] if last_state else False

    curr_epss  = current_epss
    curr_cvss  = current_nvd["cvss_score"]
    curr_patch = current_nvd["patch_known"]

    epss_delta = curr_epss - prev_epss

    # Priority order: most severe change wins
    if last_state is None:
        change_type = "new_cve"
        summary = f"First scan of {cve_id}: EPSS={curr_epss:.3f}, CVSS={curr_cvss}"
    elif curr_epss >= EPSS_CRITICAL_THRESHOLD and prev_epss < EPSS_CRITICAL_THRESHOLD:
        change_type = "epss_critical"
        summary = f"EPSS crossed critical threshold: {prev_epss:.3f} → {curr_epss:.3f} (>{EPSS_CRITICAL_THRESHOLD})"
    elif epss_delta >= EPSS_SPIKE_THRESHOLD:
        change_type = "epss_spike"
        summary = f"EPSS spiked by {epss_delta:.3f}: {prev_epss:.3f} → {curr_epss:.3f}"
    elif curr_patch and not prev_patch:
        change_type = "new_patch"
        summary = f"Patch became available (EPSS={curr_epss:.3f}, CVSS={curr_cvss})"
    elif curr_cvss > prev_cvss and (curr_cvss - prev_cvss) >= 1.0:
        change_type = "severity_increase"
        summary = f"CVSS score increased: {prev_cvss} → {curr_cvss}"
    else:
        change_type = "no_change"
        summary = f"No significant change (EPSS={curr_epss:.3f}, CVSS={curr_cvss})"

    return ChangeSignal(
        cve_id=cve_id,
        change_type=change_type,
        previous_epss=prev_epss,
        current_epss=curr_epss,
        previous_cvss=prev_cvss,
        current_cvss=curr_cvss,
        patch_newly_available=(curr_patch and not prev_patch),
        summary=summary,
    )

Read the order of the if branches. The first match wins:

  1. no earlier state: new_cve
  2. EPSS crossed 0.50 on this scan: epss_critical
  3. EPSS rose by at least 0.15: epss_spike
  4. a patch signal appeared that was not there before: new_patch
  5. CVSS rose by at least 1.0: severity_increase
  6. otherwise: no_change

The thresholds are two named constants at the top of the file: EPSS_SPIKE_THRESHOLD = 0.15 and EPSS_CRITICAL_THRESHOLD = 0.50.

Why not ask the model "did anything important change?" The docstring explains: a model might treat the same small movement as significant on one run and not on the next. Code gives the same answer every time, can be unit tested, and can be audited. This is a pattern worth copying: use deterministic code for decisions you must be able to explain, and use the model for language.

Turning a change into an alert

Only when the rules find a change does the model get involved:

levels/l6_autonomous.py · generate_alert
async def generate_alert(signal: ChangeSignal) -> AutonomousAlert:
    """
    Given a detected change, ask the LLM to generate a clear, actionable alert.

    The WHAT (change_type, deltas) is already determined by detect_changes().
    The LLM's job here is the HOW: phrase the alert clearly and recommend
    the right action. This is a single, focused LLM call — not a multi-step chain.

    Severity mapping:
      epss_critical, new_cve (high EPSS)  → Critical
      epss_spike, severity_increase       → Warning
      new_patch, everything else          → Informational
    """
    severity_map = {
        "epss_critical":   "Critical",
        "epss_spike":      "Warning",
        "severity_increase": "Warning",
        "new_patch":       "Informational",
        "new_cve":         "Warning" if signal.current_epss > 0.3 else "Informational",
        "no_change":       "Informational",
    }
    severity = severity_map.get(signal.change_type, "Warning")

    response = await client.chat.completions.create(
        model=MODEL,
        messages=[
            {
                "role": "system",
                "content": (
                    "You are an autonomous security monitoring agent. "
                    "A change has been detected in a tracked CVE. "
                    "Write a clear, concise alert and a specific recommended action. "
                    "Be direct — this alert goes to security engineers who need to act fast."
                ),
            },
            {
                "role": "user",
                "content": (
                    f"CVE: {signal.cve_id}\n"
                    f"Change detected: {signal.summary}\n"
                    f"Previous EPSS: {signal.previous_epss:.4f} | Current EPSS: {signal.current_epss:.4f}\n"
                    f"Previous CVSS: {signal.previous_cvss} | Current CVSS: {signal.current_cvss}\n"
                    f"Patch newly available: {signal.patch_newly_available}\n"
                    f"Alert severity: {severity}\n\n"
                    "Generate the alert summary and recommended action."
                ),
            },
        ],
        response_format={
            "type": "json_schema",
            "json_schema": {
                "name":   "AutonomousAlert",
                "strict": True,
                "schema": _strict_schema(AutonomousAlert),
            },
        },
        temperature=0.1,
        max_tokens=512,
    )

    alert = AutonomousAlert.model_validate(
        json.loads(response.choices[0].message.content)
    )
    # Ensure the structured fields match what we detected — LLM fills in text,
    # we control the severity, scores, and type deterministically
    return AutonomousAlert(
        cve_id=signal.cve_id,
        alert_type=signal.change_type,
        severity=severity,
        summary=alert.summary,
        recommended_action=alert.recommended_action,
        epss_now=signal.current_epss,
        cvss_now=signal.current_cvss,
        auto_generated=True,
    )

Look at what the code does after the model replies. It builds the final alert from the rule-based signal: the severity, the alert type and the scores all come from code. The model supplies only two pieces of text, the summary and the recommended action. So the model cannot talk its way into a higher or lower severity.

The mapping, from the severity_map inside the function, is:

ChangeAlert severity
epss_criticalCritical
epss_spike, severity_increaseWarning
new_patch, no_changeInformational
new_cveWarning if the EPSS score is above 0.3, otherwise Informational

Scanning one CVE

scan_one runs the whole cycle for one CVE: fetch, compare, save the new baseline, and alert if needed.

levels/l6_autonomous.py · scan_one
async def scan_one(cve_id: str, db_url: str = DB_URL) -> AutonomousAlert | None:
    """
    Run a complete scan cycle for one CVE:
      1. Fetch current NVD + EPSS data in parallel (L2 pattern)
      2. Load last known state from scan_state table
      3. Detect whether anything significant changed
      4. If yes: generate an alert and save it
      5. Always: update scan_state and last_scanned timestamp

    Returns the generated Alert if one was created, None otherwise.

    CONCURRENCY NOTE: Each call opens and closes its OWN database connection.
    asyncpg connections are not safe for concurrent operations on the same
    connection object — overlapping awaits raise "another operation is in
    progress". Because scan_all_once() calls this function for every CVE in
    parallel via asyncio.gather(), each task must own its connection exclusively.
    Using separate connections (or a pool) is the standard fix.
    """
    # Open a private connection for this task — safe for concurrent callers
    conn = await asyncpg.connect(db_url)
    try:
        # Fetch NVD and EPSS simultaneously — L2's parallel pattern applied here.
        # Note: these are pure HTTP calls, not DB operations, so they don't touch
        # our connection and are safe to run in parallel.
        nvd_data, epss_score = await asyncio.gather(
            fetch_current_nvd(cve_id),
            fetch_current_epss(cve_id),
        )

        last_state = await get_scan_state(conn, cve_id)
        signal     = detect_changes(cve_id, last_state, nvd_data, epss_score)

        # Save the current state as the new baseline, regardless of whether we alert
        await save_scan_state(conn, cve_id, epss_score, nvd_data["cvss_score"], nvd_data["patch_known"])
        await mark_last_scanned(conn, cve_id)

        if signal.change_type == "no_change":
            return None  # Nothing to alert on

        # Significant change: ask the LLM to phrase the alert clearly
        alert    = await generate_alert(signal)
        alert_id = await save_alert(conn, alert)
        console.print(
            f"  [bold {'red' if alert.severity == 'Critical' else 'yellow'}]"
            f"  ALERT #{alert_id} [{alert.severity}] {cve_id}: {signal.change_type}[/bold {'red' if alert.severity == 'Critical' else 'yellow'}]"
        )
        return alert
    finally:
        await conn.close()

Two details matter.

  • One connection per task. Many scans run at the same time, and a database connection cannot be shared by overlapping operations. So each scan_one opens and closes its own. The comment in the code names the error you would otherwise hit.
  • The baseline is saved whether or not an alert fires. That way the next scan always compares against the most recent numbers.

Scanning the whole watchlist

levels/l6_autonomous.py · scan_all_once
async def scan_all_once(db_url: str = DB_URL) -> dict:
    """
    Run one complete pass over the entire watchlist.
    Scans all CVEs in parallel (up to a concurrency cap to avoid rate limits).

    Returns a summary dict: how many CVEs scanned, how many alerts generated.
    This function can be called standalone (e.g. from the CLI) without the
    background loop running.
    """
    conn = await asyncpg.connect(db_url)
    try:
        await init_db_l6(conn)
        watchlist = await get_watchlist(conn)

        if not watchlist:
            # Use "alerts_created" (not "alerts") to match what _monitor_loop reads.
            return {"scanned": 0, "alerts_created": 0, "message": "Watchlist is empty"}

        console.print(f"[dim]  Scanning {len(watchlist)} CVE(s)...[/dim]")

        # Scan all CVEs simultaneously. We cap concurrency at 5 to avoid
        # hammering the NVD API (which rate-limits at 5 req/30s without a key).
        #
        # IMPORTANT: scan_one() opens its own connection per task. We do NOT
        # pass the parent `conn` here — that would share one connection across
        # multiple concurrent DB operations, triggering asyncpg's
        # "another operation is in progress" error.
        sem     = asyncio.Semaphore(5)
        alerts_generated = 0

        async def _scan_with_sem(entry):
            async with sem:
                return await scan_one(entry["cve_id"], db_url)

        results = await asyncio.gather(
            *[_scan_with_sem(entry) for entry in watchlist],
            return_exceptions=True,  # Don't let one failure stop the whole scan
        )

        for r in results:
            if isinstance(r, Exception):
                console.print(f"[dim red]  scan error: {r}[/dim red]")
            elif r is not None:
                alerts_generated += 1

        return {
            "scanned":        len(watchlist),
            "alerts_created": alerts_generated,
            "timestamp":      datetime.now(timezone.utc).isoformat(),
        }
    finally:
        await conn.close()

The scans run in parallel, but a semaphore limits it to 5 at a time, because the public NVD API rate-limits callers. return_exceptions=True means one failing CVE does not stop the others; the error is printed and the scan continues.

The loop, and the kill switch

The loop itself is short. It scans, then waits, then repeats until told to stop:

levels/l6_autonomous.py · _monitor_loop
async def _monitor_loop(db_url: str) -> None:
    """
    The perpetual background loop.

    Each iteration: scan everything → sleep → repeat.
    The sleep uses _stop_event.wait(timeout=...) so the kill switch takes
    effect immediately rather than waiting out the current sleep interval.

    This function is meant to run as an asyncio.Task — call start_monitor()
    to create it, stop_monitor() to cancel it.
    """
    console.print(f"[green]  Autonomous monitor started. Scan interval: {SCAN_INTERVAL_SECONDS}s[/green]")

    while not _stop_event.is_set():
        scan_start = time.perf_counter()
        try:
            summary = await scan_all_once(db_url)
            elapsed = time.perf_counter() - scan_start
            console.print(
                f"[dim]  Scan complete: {summary['scanned']} CVEs, "
                f"{summary['alerts_created']} alerts, {elapsed:.1f}s[/dim]"
            )
        except Exception as e:
            console.print(f"[red]  Monitor loop error: {e}[/red]")

        # Sleep until next interval — but wake up instantly if stop is requested.
        # asyncio.wait_for raises TimeoutError after SCAN_INTERVAL_SECONDS,
        # which we catch as "time to scan again". If stop fires, the wait returns
        # early and the while condition fails.
        try:
            await asyncio.wait_for(_stop_event.wait(), timeout=SCAN_INTERVAL_SECONDS)
        except asyncio.TimeoutError:
            pass  # Expected — means the interval elapsed normally

    console.print("[yellow]  Autonomous monitor stopped.[/yellow]")

The waiting is done with asyncio.wait_for on a stop event rather than a plain sleep, so a stop request wakes the loop immediately instead of after the full interval. The interval comes from VIGIL_SCAN_INTERVAL in seconds, and the code's default is 3600 (one hour); the comment suggests 60 for demos.

The emergency brake is stop_monitor:

levels/l6_autonomous.py · stop_monitor
async def stop_monitor() -> bool:
    """
    Kill switch: immediately stop all autonomous monitoring activity.

    Sets the stop event (causes the loop to exit on its next check),
    then cancels the task (wakes it from any current sleep immediately).
    Returns True if a running task was stopped, False if nothing was running.
    """
    global _monitor_task

    if not is_running():
        return False

    _stop_event.set()
    _monitor_task.cancel()
    try:
        await _monitor_task
    except asyncio.CancelledError:
        pass  # Expected — we cancelled it

    _monitor_task = None
    return True

It sets the stop event, cancels the task, waits for it to finish, and reports whether something was actually running. Calling it when nothing is running is harmless. The loop is started by start_monitor, which also does nothing if one is already running.

Note

The loop is an asyncio.Task inside one Python process, which here means inside the API server. If the server restarts, the loop stops and has to be started again. The code comments say a real deployment would use a proper scheduler.

Human oversight

The code is clear about the limits of its own authority. The agent detects and alerts; it does not act. It does not patch systems, open tickets or send email. In the header's words: full autonomy in detection, human authority in response.

Two controls support that:

  • The kill switch, POST /l6/monitor/stop, stops all autonomous activity.
  • Alert acknowledgement, POST /l6/alerts/{id}/acknowledge, records who reviewed an alert and when, using the acknowledged, acknowledged_at and acknowledged_by columns. Unacknowledged alerts stay visible, so there is a trail of what was reviewed.

This is the human-in-the-loop idea in its simplest form: the system proposes, a person decides. For the wider treatment of limiting what an agent may do, see Action governance.

Setting it up

L6 needs the same PostgreSQL setup as Level 5, so follow its "Setting up PostgreSQL" section. In short, docker compose up --build starts the database, and the scripts default to localhost:5432.

Run it

The command line covers the manual parts:

python levels/l6_autonomous.py --add CVE-2021-44228
python levels/l6_autonomous.py --add CVE-2023-44487
python levels/l6_autonomous.py --scan
python levels/l6_autonomous.py --status

--scan performs one pass over the watchlist and prints how many CVEs were scanned and how many alerts were generated. --status shows the watchlist and the most recent alerts. There is also --remove to take a CVE off the list.

The continuous loop is not started from the command line. It runs inside the API server:

curl -X POST http://localhost:8000/l6/monitor/start
curl http://localhost:8000/l6/monitor/status
curl -X POST http://localhost:8000/l6/monitor/stop

Other endpoints cover the watchlist (/l6/watchlist), a manual scan (/l6/scan) and alerts (/l6/alerts). The web interface has an L6 page with the same controls.

What to expect from the code, step by step: the first scan of a CVE has no saved state, so it is classified new_cve and an alert is generated for it, even if the risk is low, because the code only skips alerting on no_change. From the second scan on, an alert appears only if one of the rules fires. Check the values against NVD and EPSS yourself: the numbers are live and change over time.

Try it

Try it

1) Add two CVEs and run --scan twice in a row. Compare the alerts after the first and the second scan. Which change types appear? 2) Lower EPSS_SPIKE_THRESHOLD and VIGIL_SCAN_INTERVAL, start the monitor through the API, then watch the console output. 3) Call the kill switch twice and notice that the second call reports nothing was running. 4) Acknowledge an alert through the API and check that --status now marks it reviewed. 5) Add a unit test for detect_changes: it is a pure function, so you can feed it dictionaries and assert the change type, with no database or model.

Common mistakes and limits to know about

  • Letting the model decide what is significant. Keep the decision in code, as this level does.
  • Alert fatigue. Every non-no_change result produces an alert and a model call, including the first sighting of each CVE. Too many alerts teach people to ignore them. Tune the thresholds.
  • Fetch failures look like data. fetch_current_epss returns 0.0 on any error, and scan_one then saves that as the new baseline. A one-off network failure can therefore be recorded as "EPSS is 0", and the next successful scan may look like a spike. Treating "no data" and "zero" as different things is a worthwhile improvement.
  • Header comments that describe more than the code does. The file's header mentions ignoring CVEs that already have "patched" feedback, and a noise band below 0.05. detect_changes implements neither. Always confirm behaviour in the code.
  • No kill switch. Anything that runs on its own needs a documented way to stop it.
  • Believing it acts. This agent only informs. Do not give an autonomous loop write access to production systems without the controls in Action governance and review of its decisions.

Check yourself

What is the difference between automated and autonomous in this project?

Automated systems run when a person or trigger starts them. An autonomous system starts its own work on a schedule or goal. L6 is autonomous because the loop scans the watchlist without being asked.

Why is change detection plain Python instead of a model call?

It must be consistent, testable and explainable. A model might judge the same small change differently on different runs. The model is used only to write the alert text.

Who sets an alert's severity, the code or the model?

The code. The final alert takes its severity, type and scores from the rule-based signal, and only the summary and recommended action come from the model.

Why does each scan open its own database connection?

Scans run concurrently, and a single connection cannot handle overlapping operations. Each task owns its connection to avoid the "another operation is in progress" error.

What does the kill switch do, and is it safe to call twice?

It sets the stop event and cancels the background task, so the loop ends at once. A second call finds nothing running and simply reports that.
