Architectures

Architectures: four ways to build the same agent

The question this track answers: once a model can call tools, how should you organise it?

The levels teach capabilities in order: one call, a chain, parallel agents, routing, tools, memory, autonomy. The architectures are different. Each one is a named design pattern, and Vigil gives all four the same job so you can compare them fairly:

Note

Investigate a CVE using live data from NVD, EPSS and the CISA Known Exploited Vulnerabilities (KEV) catalog, then produce a structured risk report.

Same tools, same kind of report, four different designs. The differences you see are the differences in the pattern, not in the task.

The three tools they share

ToolSourceWhat it tells you
fetch_nvd_dataNVDDescription, CVSS score, severity
fetch_epss_scoreEPSSProbability the CVE is exploited soon (0 to 1)
check_cisa_kevCISA KEVWhether the CVE is confirmed as actively exploited

KEV is the new one compared with L4. A CVE in the KEV catalog is being exploited in the wild, which is the strongest urgency signal the project uses.

Which one should I use?

This comparison comes from reading how each file is built. It is qualitative on purpose: real cost and speed depend on the model, the CVE and your network, and Vigil does not measure them here.

A1 ReActA2 Plan-and-ExecuteA3 ReflectionA4 Multi-agent
Who decides the next stepThe model, after seeing each resultThe model, once, up frontFixed code (research, critique, revise)Fixed code dispatches; each specialist chooses its own tool calls
Model callsAs many as the loop needs, plus one to structure the reportTwo: one plan, one synthesis. Tool steps call your code directlyThree, alwaysSeveral per specialist, three specialists, plus one orchestrator call
ParallelismTool calls within one model turn run togetherSteps run one by oneThe three data fetches run together; the three model calls are sequentialThe three specialists run together
Main strengthAdapts to what it finds; shows its reasoningPredictable; you can review or edit the plan before anything runsImproves report quality by checking itFocused roles; independent work finishes sooner
Main weaknessLess predictable; can wanderCannot change course after the plan is madeDoes not gather more data; only rewritesMost moving parts; specialists cannot see each other
Reach for it whenThe path depends on what you discover, or you need an audit trail of reasoningYou need approval before acting, or want a fixed, inspectable procedureThe wording and calibration of the answer mattersThe work splits into independent, specialised jobs
Tip

They combine. The Reflection file says so itself: gather data with ReAct, then critique the resulting report. Real systems often layer two patterns.

Running them

Each file is a script. They call the OpenAI API and the three live public data sources, so you need a key in .env and an internet connection.

python architectures/a1_react.py CVE-2021-44228
python architectures/a2_plan_execute.py CVE-2021-44228
python architectures/a3_reflection.py CVE-2021-44228
python architectures/a4_multi_agent.py CVE-2021-44228
Note

The tests in tests/test_architectures.py replace the model and the data fetchers with stand-ins, so they run offline and cost nothing. They check the control flow: the order of calls, the safety limits, and how errors are handled. They do not check how good a real model's answers are.

The LangGraph bridge

Frameworks such as LangGraph give you ready-made building blocks for this kind of orchestration. Vigil writes its patterns by hand so you can see how they work, then shows how they map onto a framework in architectures/frameworks/.

MAPPING.md lists the correspondence:

Vigil conceptLangGraph concept
A Python function that updates stateA graph node
if/else routing inside the loopA conditional edge
The messages listA field in the graph state
The max_iterations guardrecursion_limit
The tool dispatch functionA tool node or callable

The same file notes that CrewAI maps to A4, LlamaIndex to the L5 memory work, and the OpenAI Agents SDK to the L4 tool loop.

The code is a deliberately small port, a1_react_langgraph.py:

architectures/frameworks/a1_react_langgraph.py · build_graph
def build_graph():
    """Build the LangGraph graph. Raises ImportError if langgraph is absent."""
    from langgraph.graph import END, START, StateGraph

    async def reason(state: GraphState) -> GraphState:
        cve_id = state["cve_id"]
        client = AsyncOpenAI(timeout=45.0)
        response = await client.chat.completions.create(
            model=MODEL,
            messages=[
                {"role": "system", "content": "You are a concise vulnerability analyst."},
                {"role": "user", "content": f"Give a one-line remediation verdict for {cve_id}."},
            ],
            temperature=0.1,
            max_tokens=120,
        )
        verdict = (response.choices[0].message.content or "").strip()
        return {**state, "verdict": verdict}

    graph = StateGraph(GraphState)
    graph.add_node("reason", reason)
    graph.add_edge(START, "reason")
    graph.add_edge("reason", END)
    return graph.compile()

Read it honestly: it builds a graph with one node (reason) that makes a single model call and returns a one-line verdict. It does not reproduce A1's tool loop. It exists to show the vocabulary of nodes, edges and state, not to be a full port.

If LangGraph is not installed, analyse_cve catches the ImportError and returns a canned fallback sentence with "framework": "fallback", so nothing crashes. That fallback does not call a model. Install the real thing with pip install -e ".[frameworks]". The API exposes the port at /frameworks/a1.

Try it

Try it

Run all four on the same CVE and compare, in a notebook or a text file: how many tool calls each made, how long each took (each script prints it), and how the final risk verdicts differ in wording and caution. Then run a CVE that is not in the KEV catalog and see which pattern copes best with the "not found" answer.

Common mistakes

  • Treating the patterns as rivals. They solve different problems. Pick by what you need, not by which sounds most advanced.
  • Reaching for multi-agent first. More agents means more calls, more cost and more places to fail. Use one only when the job really splits.
  • Assuming reasoning text is the real reason. In ReAct the written Thought is useful evidence, but it is text the model produced, not a guaranteed view into its process.
  • Skipping limits. Every loop here has a cap. Keep that habit in your own agents.

Check yourself

What is held constant across A1 to A4, and why?

The job and the tools (NVD, EPSS, CISA KEV) and the shape of the report. Holding them constant means any difference in behaviour comes from the pattern.

Which pattern lets a human approve a step before anything runs, and why?

Plan-and-Execute (A2). Because the plan exists as data before execution starts, a person can review, edit or reject it.

Why is the LangGraph port in Vigil only one node?

It is a minimal illustration of the framework's vocabulary. It makes one model call and returns a verdict, and it does not include A1's tool loop.
