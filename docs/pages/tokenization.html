Tokenization and context economics

The question this topic answers: what exactly am I paying for, and how much text fits in one call?

You met tokens in How LLMs work. This page lets you see them. Models read and bill in tokens, and every model has a context window, a ceiling on tokens per call. Knowing your token count is the first step in controlling cost, avoiding cut-off input, and sizing anything you feed a model.

The idea in plain English

A tokenizer chops text into pieces from a fixed vocabulary. Common words are often one piece. Rare strings, identifiers and punctuation get split into more pieces. That is why a short-looking CVE identifier can cost several tokens, while a plain English word costs one.

Counting tokens

The module uses tiktoken, the tokenizer library used with OpenAI models, to count tokens exactly.

levels/foundations/tokenization.py · count_tokens
def count_tokens(text: str, model: str = MODEL) -> int:
    """Return the exact tiktoken count for text/model."""
    enc = _get_encoding(model)
    return len(enc.encode(text))

The helper behind it picks the tokenizer that matches your model, and falls back to a general-purpose one if the model name is unknown:

levels/foundations/tokenization.py · _get_encoding
def _get_encoding(model: str):
    import tiktoken

    try:
        return tiktoken.encoding_for_model(model)
    except Exception:
        return tiktoken.get_encoding("cl100k_base")
Note

tiktoken is an optional package (the foundations and tokens extras). The first run may also need to fetch a tokenizer vocabulary file, so it can need a network connection once. The notebook 01_tokenization.ipynb uses a built-in fallback of roughly four characters per token so it works fully offline, which is an approximation, not an exact count.

Looking inside

show_tokens returns the first few tokens as an index, an id and the decoded text, so you can see where the cuts fall:

levels/foundations/tokenization.py · show_tokens
def show_tokens(text: str, model: str = MODEL, limit: int = 32) -> list[dict[str, Any]]:
    """Return token ids + decoded pieces for inspection."""
    enc = _get_encoding(model)
    ids = enc.encode(text)
    rows: list[dict[str, Any]] = []
    for i, tok in enumerate(ids[:limit]):
        rows.append({"i": i, "id": tok, "piece": enc.decode([tok])})
    return rows

Notice that a piece can include a leading space. That is normal: spaces are part of tokens.

From tokens to a budget report

tokenize_report combines the count with the pricing helper from vigil/pricing.py to show how full the context window is and what the prompt would cost:

levels/foundations/tokenization.py · tokenize_report
def tokenize_report(text: str, model: str = MODEL, completion_tokens_estimate: int = 0) -> dict[str, Any]:
    """Build a budget/cost report for one text snippet."""
    report = budget_report(
        model=model,
        prompt_tokens=count_tokens(text, model=model),
        completion_tokens=completion_tokens_estimate,
    )
    return {
        "model": model,
        "text_preview": (text[:120] + "...") if len(text) > 120 else text,
        "token_count": report["prompt_tokens"],
        "context_limit": report["context_limit"],
        "pct_of_context": report["pct_of_context"],
        "est_cost_usd": report["estimated_cost_usd"],
        "sample_tokens": sample_tokens(text, model=model),
    }

The fields to read:

FieldMeaning
token_countExact tokens in your text for the chosen model
context_limitThe model's token ceiling, from the table in vigil/pricing.py
pct_of_contextHow much of that ceiling this text uses
est_cost_usdAn estimate from indicative list prices; not a bill
sample_tokensThe first few pieces, so you can inspect the boundaries
Warning

The cost is an estimate from prices copied into the code. Providers change prices, so use it for relative comparisons, not budgeting.

Run it

python levels/foundations/tokenization.py "CVE-2021-44228 RCE in Log4j"

You should get a report dictionary and a table of the first tokens, each with its id and decoded piece. This needs tiktoken, so install the foundations extra if you have not: pip install -e ".[foundations]".

The same report is available over the API at POST /foundations/tokenize, and in the Streamlit interface.

Why it matters later

  • Cost. Billing scales with tokens in and out. Longer prompts and longer answers cost more.
  • Cut-off. If input plus reply exceeds the context window, something has to give. The L5 memory code builds a budgeted context for exactly this reason; see build_budgeted_memory_context in levels/l5_memory.py.
  • Chains and fan-out. Every extra step you add in L1 or L2 repeats tokens, so token awareness shapes how you design them.

Which costs more tokens per character? 2) Tokenize the same sentence in lower case, upper case and with extra punctuation. 3) Paste a long advisory and read pct_of_context. How many copies would it take to overflow the window? 4) Use --model with a different model name and compare counts.

Common mistakes

  • Counting characters or words instead of tokens. The ratio changes with the text, so count properly.
  • Forgetting the reply. The window covers your input and the model's output.
  • Assuming one tokenizer fits all models. Different model families split text differently, so counts from one are only a rough guide for another.
  • Trusting the estimated cost. It is a teaching figure from fixed prices.

Check yourself

Why can a short identifier cost more tokens than a short English word?

Tokenizers are built from common text. Common words are single pieces; rare strings, digits and symbols are split into several smaller ones.

What two limits do token counts control?

Cost (you pay per token) and the context window (the maximum tokens per call, input plus output).

Is est_cost_usd a bill?

No. It is computed from indicative list prices stored in vigil/pricing.py, which can be out of date.
